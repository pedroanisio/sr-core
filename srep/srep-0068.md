# SREP 68 — Step stateful effects per node, with prewarm and checkpoints

## Abstract

A shader effect with persistent ISF buffers gains two attributes: `stepsPerFrame` (how many steps it advances
per frame) and `prewarm` (how many steps it runs before the node's first frame). This SREP also defines the effect's
state at any frame as a function of that node alone. The picture at frame f must then be the same whether frames
were rendered in order, after a seek, or in a separate segment process. Engines are allowed to save **state
checkpoints**, keyed by content hash and frame, so that a seek or a segment render resumes from the nearest
checkpoint and re-runs only that node, not the whole scene. With both attributes at their defaults, the picture is
the one rendered today.

## Motivation

**The owner's 72-cell atlas test (2026-10-09, not published).** Reaction–diffusion (Gray–Scott) and similar cells
use a persistent ISF shader. To reach frame N, the engine re-renders every earlier frame of the whole scene, so in
a 72-cell atlas each Gray–Scott step also pays for the Mandelbulb and the other 70 cells. The owner asked for
"steps per frame" and prewarm defined per node. The plan ranks this, with SREP 69 (agents), after accumulation
(SREP 67). It also makes segment renders and seeks cheaper.

**What the reference does today** (`rs-scene-render` commit `c09b58a`):

- **Detection.** `crates/sr-gpu/src/shader.rs`, `has_persistent`: a scene "has persistent shaders" when any
  `effect type="shader"` declares an ISF pass with `"PERSISTENT": true`.
- **Replay.** `crates/sr-gpu/src/render.rs`, `render_with`, lines 3259–3274: when a requested frame does not follow
  the previous one, the renderer restores the latest checkpoint at or before it (`fx.restore`). It then renders
  **the whole frame graph** (`render_graph`) for every frame from there up to the requested one.
- **Checkpoints.** `crates/sr-gpu/src/shader.rs`, `checkpoint`, lines 1186–1195: about once per second (every
  `round(fps)` frames), in memory, at most 33 plus frame 0, and only within one process. A segment render in
  another process starts from frame 0.
- **Steps.** One step per rendered frame. There is no step count and no prewarm.
- **Particles.** `particleEmitter/@preroll` (seconds) is the only existing "start before the first frame"
  attribute. It applies to particles only.

## Specification

### Syntax

```xml
<!-- effectType gains -->
<xs:attribute name="stepsPerFrame" default="1">
  <xs:annotation><xs:documentation>type="shader" with PERSISTENT passes: steps (evaluations of all passes) per frame. SREP 68.</xs:documentation></xs:annotation>
  <xs:simpleType><xs:restriction base="xs:positiveInteger"><xs:maxInclusive value="10000"/></xs:restriction></xs:simpleType>
</xs:attribute>
<xs:attribute name="prewarm" default="0">
  <xs:annotation><xs:documentation>Steps run before the node's first active frame, with the inputs of that frame. SREP 68.</xs:documentation></xs:annotation>
  <xs:simpleType><xs:restriction base="xs:nonNegativeInteger"><xs:maxInclusive value="10000000"/></xs:restriction></xs:simpleType>
</xs:attribute>
```

```xml
<sch:pattern id="p-srep68">
  <sch:rule context="effects/effect[@stepsPerFrame or @prewarm]">
    <sch:assert id="STP1" test="@type='shader'">stepsPerFrame and prewarm apply to shader effects only.</sch:assert>
  </sch:rule>
</sch:pattern>
```

No version gate applies. Under SREP 4, new attributes with neutral defaults are accepted in every version. (SREP 69
extends STP1 to stepping programs.)

### Semantics

**1. Steps.** Take a stateful pair (E, n), where E is a shader effect with persistent passes applied to node n.
Let f₀ be n's first active frame: the first frame whose time lies in n's timing window, after timing resolution.
Let k = `stepsPerFrame` and p = `prewarm`.

- **State at f₀ − 1.** The state "before frame f₀" is the zero state (all persistent buffers zero), advanced p
  steps with n's input at time t(f₀).
- **State at frame f ≥ f₀.** The state at f is the state at f − 1 advanced k steps with n's input at time t(f).
  All k steps of a frame see the same input and the same time uniforms.
- **What is drawn.** The picture drawn at frame f is the output of the last of those steps.

After frame f the pair has taken p + (f − f₀ + 1)·k steps.

- **Uniforms.** For the steps of frame f: `TIME` is t(f), `TIMEDELTA` is 1/(fps·k), and `FRAMEINDEX` is the number
  of steps taken before this one, counting the prewarm steps from 0.
- **Input.** n's input at time t is what the effect reads as `inputImage` at t: n's own content, as the shader
  effect receives it today.

A frame at which n is outside its window takes no steps. When n is active again, it continues from its last state.

**2. The state depends on the node alone (normative).** The state of (E, n) at frame f is a function only of:

- E's attributes and source;
- n's input at frames f₀ … f;
- `project/@seed`;
- `project/@fps`.

It does not depend on other nodes, except through n's own content, nor on which frames were rendered before, in
what order, or in which process.

An engine MUST render frame f of a document identically whether it:

- renders frames 0 … f in order;
- renders f alone after a seek;
- renders f as the first frame of a segment in a separate process.

To reach frame f, an engine needs to evaluate only n's subtree at the earlier frames, not the whole scene.

**3. Checkpoints.** An engine MAY save the state of (E, n) after a frame and resume from it. A resumed render
MUST be identical to one computed from f₀ (2). A checkpoint saved where another process or another run can read it,
such as a cache directory, MUST be keyed by the SHA-256 of the UTF-8 bytes of:

    "sr-checkpoint-1" NUL engine NUL engineVersion NUL sha256(E's canonical XML) NUL sha256(E's shader source)
    NUL sha256(n's canonical XML subtree) NUL sha256 of every file that subtree reads, in document order
    NUL decimal(project/@seed) NUL fps NUL decimal(f)

- The canonical XML is Canonical XML 1.1 without comments. "engine" and "engineVersion" identify the engine
  build. Checkpoints hold float state, so they are not portable between engines or builds.
- An engine MUST NOT load a checkpoint whose key differs.
- An engine SHOULD report checkpoint hits and misses in the render report (SREP 18).

**4. Inside `iterate`.** A pair inside an `iterate` (SREP 67) ignores `stepsPerFrame` and `prewarm`. The `iterate`
defines its steps.

### Defaults and the neutral case

With k = 1 and p = 0, Semantics 1 takes one step per frame, beginning at the node's first active frame. That is
what the reference does today for a node that is drawn at every frame of its window.

**Not verified:** whether the reference also skips the step at a frame where the node is in its window but not
drawn, for example at opacity 0 or masked out entirely. If it skips that step, Semantics 1 (one step per active frame,
drawn or not) differs from today for such nodes. Before acceptance, either the reference is checked and the text
matches it, or the difference is listed here as a change.

## Rationale

- **Per node, not per scene.** The cost of a step is then the cost of that node. A scene-wide count would make every
  node pay for the slowest simulation.
- **Steps share their frame's input.** This is the simplest rule that is exact: sub-step interpolation of the input
  would need the node's content at times that are not frame times.
- **Prewarm in steps, not seconds.** Seconds would make the step count depend on fps. `particleEmitter/@preroll`
  uses seconds because particles integrate in time; persistent shaders count steps.
- **Order independence is normative.** Film builds render segments in separate processes and join them (internal
  production records, 2026-10-07 to 2026-10-09). A stateful effect that depended on
  render order would break those joins.
- **Keys include the engine build.** The state is float data that an engine computes on the GPU. Two builds may
  differ in their last bits, and loading one build's state into another would silently mix the two.

## Rejected alternatives

- **A scene-wide `<iterate>` for animation** (SREP 67): every step would re-render every node.
- **Defining steps in time units** (`stepRate` in steps per second): it needs rounding rules at every frame, and it
  changes with `fps`.
- **Normative checkpoint spacing.** How often to checkpoint is a cost trade-off with no effect on the picture, so it
  is engine-only (SREP 0, "engine-only options").

## Backwards compatibility

The change is MINOR: two new attributes with neutral defaults, accepted in every version. Documents that do not
use them render as before, apart from the unverified case under **Defaults**. Today the reference already replays
from frame 0 or from a checkpoint to keep renders order-independent within one process. Semantics 2 makes this
normative across processes too.

## Conformance

The cases are in `conformance/srep_cases/srep-0068.json`, written with the shader `srep_cases/assets/srep68-counter.fs`
by `conformance/tools/srep68_cases.py`. The shader counts its steps in a persistent float buffer. It draws red once
the count reaches the parameter `target`, and blue before. Each pair of cases sets `target` to the step count of
Semantics 1 and to one more, so the pair checks the count exactly. All cases are pending.

| Case | Checks | Tolerance |
|---|---|---|
| `srep-0068-one-step-per-frame`, `-short` | neutral defaults: 1 step at frame 0 | 2 px |
| `srep-0068-steps-per-frame`, `-short` | `stepsPerFrame="10"`: 10 steps at frame 0 | 2 px |
| `srep-0068-prewarm`, `-short` | `prewarm="9"`: 10 steps at frame 0 | 2 px |
| `srep-0068-seek`, `-short` | an encode that starts at 0.4 s (frame 4) shows 5 steps (2) | 2 px |
| `srep-0068-seek-combined`, `-short` | k = 3, p = 2: 17 steps at frame 4 (1, 2) | 2 px |
| `srep-0068-late-start`, `-short` | a node first active at frame 2 has taken 3 steps at frame 4 (1) | 2 px |
| `srep-0068-not-a-stateful-effect` | STP1 | exact |

The pair `one-step-per-frame` uses only today's syntax, apart from `version="1.6"`. It is expected to pass on the
reference as it stands once the version is accepted. This has not been run.

## Open issues

- The unverified behaviour at frames where a node is active but not drawn (Defaults).
- Simulations with their own clocks (`flock`, `fluid`, `slime`, `erosion`) could take the same attributes. They are
  stepped by time, not per frame, and are left to a separate SREP.
- A stateful effect applied to a node inside an `instance` or a `repeat` has one state per copy. Seeds per copy
  are not defined here.
