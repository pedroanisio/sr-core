# SREP 83 — Version gates of the 1.3 extensions admit later versions (amends SREP 40)

## Abstract

SREP 40 gates its constructs on `scene/@version="1.3"` exactly: V8 (volume assets, media, pyro and volume objects),
MSQ1 (mesh sequences), P3D1 (`particles3D`), OCN1 (`ocean`), CRT1 (`crater`), FRX1 (`fracture`) and GEO1 (globe
elevation). A document of version 1.4 or 1.5, and of 1.6 once a release admits it, is therefore refused when it uses
any of them. This SREP changes the seven gates to refuse only the versions before 1.3 (1.0, 1.1 and 1.2), the form
every gate of an earlier version has. No document of version 1.0 to 1.3 changes verdict; documents of 1.4 and later
that use these constructs become valid. The XSD does not change.

## Motivation

- **The gates test equality.** In sr-core 1.5.0, `schema/scene-render.sch` tests `/scene/@version='1.3'` in MSQ1
  (line 562), P3D1 (576), OCN1 (600), CRT1 (629), FRX1 (642) and GEO1 (650), and V8 fires in the rule context
  `/scene[@version!='1.3']` (509-510).
- **Later versions add nothing that should exclude them.** Schema 1.4.0 and 1.5.0 added `1.4` and `1.5` to
  `scene/@version` with "no version gate: nothing in documents changes" (`schema/CHANGELOG.md`, 1.4.0 and 1.5.0). Yet a
  document that declares 1.4 or 1.5 loses SREP 40: the kit case `srep-0040-crater` declared as 1.5 is refused by
  CRT1, and nothing else refuses it (kit case `srep-0083-crt1-version-1.5`, tested below).
- **The drafts for 1.6 make this a conflict.** The drafts SREPs 66 to 75 gate their constructs on 1.6, refusing
  1.0 to 1.5 (for example V15 of SREP 74, `viewport3D`). A 1.6 document cannot then use a crater, a fracture, an
  ocean, `particles3D`, pyro, a medium, a volume, a mesh sequence or globe elevation, nor the attributes that the drafts
  SREPs 77 to 79 add to those elements (SREP 77 on `crater`, `fracture` and `ocean`; SREP 78 on `pyro`; SREP 79 on
  `medium` and `whitewater`), because those attributes are only reachable through SREP 40's gated elements.
- **Every other gate refuses only earlier versions.** V1 and V6 refuse 1.0 (rule contexts `/scene[@version='1.0']`,
  1.5.0 lines 10 and 294); V5, V9, V10 and V11 refuse 1.0 and 1.1 (lines 21, 425, 452, 407). SREP 4 makes each schema
  MINOR release add its MAJOR.MINOR to `scene/@version` ("Documents and formats declare MAJOR.MINOR"), and a release
  that made a valid document invalid would be Breaking ("What counts as Breaking"), so the versions only accumulate. SREP 40 says documents "opt in with `scene/@version="1.3"`" and that the gate should make older
  validators reject the new syntax ("Compatibility, identity and time"); it does not say that later versions refuse
  it. Whether the equality test was intended or reflects 1.3 being the newest version when it was written is not
  recorded; this SREP does not depend on which.
- **The same change is drafted for 76 and 80.** The drafts SREP 76 (BH1) and SREP 80 (VOX1) were amended on
  2026-10-10 to refuse only 1.0 to 1.2, as the reference engine does on its branch `prep/srep-76-81-followups`
  (c2a66950). Without this SREP a black hole or cells would be admitted in a 1.6 document while the 1.3 constructs
  around them (a crater in an object of cells, CRT1; its fracture, FRX1) would not.

### Semantics

1. **The gates.** Each of V8, MSQ1, P3D1, OCN1, CRT1, FRX1 and GEO1 refuses its construct when `scene/@version` is
   `1.0`, `1.1` or `1.2`, and admits it in every other version the XSD accepts. What each gate covers is unchanged:

   | Rule | Construct | SREP 40 (1.5.0) refuses it in | This SREP refuses it in |
   |---|---|---|---|
   | V8 | `assets/volume`, any `medium`, any `pyro`, an `object3D` with `primitive="volume"` or `@volume` | every version but 1.3 | 1.0, 1.1, 1.2 |
   | MSQ1 | `assets/meshSequence` | every version but 1.3 | 1.0, 1.1, 1.2 |
   | P3D1 | `particles3D` | every version but 1.3 | 1.0, 1.1, 1.2 |
   | OCN1 | `ocean` | every version but 1.3 | 1.0, 1.1, 1.2 |
   | CRT1 | `object3D/crater` | every version but 1.3 | 1.0, 1.1, 1.2 |
   | FRX1 | `fracture` | every version but 1.3 | 1.0, 1.1, 1.2 |
   | GEO1 | an `object3D` with `terrain` and `primitive="globe"`, or with `planetRadius`, `terrainTileSize`, `terrainZoom`, `terrainMissing` or `terrainMemoryMiB` | every version but 1.3 | 1.0, 1.1, 1.2 |

2. **Later versions.** A version that a later release adds to `scene/@version` is admitted by these rules without a
   change to them: they name the versions they refuse, which are fixed, not the versions they admit.
3. **Meaning.** The constructs mean the same in every version that admits them. SREP 40 gives them no
   version-dependent meaning, and neither does this SREP.
4. **Native validators.** A validator that mirrors the Schematron in its own code MUST make the same change. The
   reference does (Engine impact).

### Errors and warnings

The seven rule ids, their contexts and what they refuse in 1.0 to 1.2 are unchanged. Their messages say "1.3 or
later" instead of "1.3". No warning is added.

### Defaults and the neutral case

No default changes. A document that is valid today is valid with this SREP and renders the same. A document of 1.4
or later that uses these constructs, refused today, is valid if nothing else refuses it, and renders as the same
document declared 1.3: in the reference, `scene/@version` is read only by the validator's rules
(`crates/sr-model/src/rules.rs`), the `info` command and the render report's scene section
(`crates/sr-deliver/src/render_report.rs`, "the declared version"), at `prep/srep-76-81-followups` c2a66950.

## Rationale

- **The purpose of a gate is kept.** A gate makes a document that uses a construct declare a version that defines
  it, so that a validator of an older schema refuses the construct explicitly (SREP 40). Every version from 1.3 on
  defines SREP 40's constructs, so admitting them there loses nothing a gate is for.
- **The form of the other gates.** V1, V5, V6, V9, V10 and V11 and the drafts' V15 list the versions they refuse.
  The SREP 40 gates were the only ones that list the version they admit.
- **A list of earlier versions, not a number.** `number(/scene/@version) >= 1.3` would read a future `1.10` as 1.1.
  The earlier versions are a closed set, so the list never needs to change.

## Rejected alternatives

- **Keep the equality and ask authors to declare 1.3.** Then no document can use SREP 40 together with any construct
  gated on a later version (SREPs 66 to 75 gate on 1.6).
- **Gate on 1.6 or later.** Every valid 1.3 document that uses these constructs, the kit's SREP 40 cases and the
  reference's corpus among them, would become invalid: Breaking under SREP 4.
- **Remove the gates.** A 1.0 to 1.2 document could then use 1.3 constructs, against SREP 40's opt-in, and a
  validator of 1.2 and one of 1.6 would disagree on a 1.2 document.

## Backwards compatibility

**Class.** Added (MINOR) under SREP 4: no valid document becomes invalid, and no valid document renders differently.
Documents that were invalid only because of these gates become valid.

**Does any 1.3-only document change verdict? No.** For `version="1.3"`, SREP 40's test `/scene/@version='1.3'` and
this SREP's test `not(/scene/@version='1.0' or /scene/@version='1.1' or /scene/@version='1.2')` are both true, and
neither V8 context (`/scene[@version!='1.3']`, `/scene[@version='1.0' or @version='1.1' or @version='1.2']`)
selects the scene, so every gate gives the same result; the diff changes no other line. For 1.0, 1.1 and 1.2 both
texts refuse. `tests/test_srep_0083.py` checks this on the kit: none of the 425 case files outside this SREP changes
verdict, and each of the 127 cases of version 1.3 keeps its verdict with SREP 83, keeps it when declared 1.0, 1.1
and 1.2, and gets its 1.3 verdict when declared 1.4 or 1.5 (against the drafts SREPs 76 to 81 for their own cases).
The reference's corpus gives the same answer (Engine impact).

**What changes.** A document of version 1.4 or 1.5 that uses a gated construct and was refused only by its gate is
valid. Such a document is still refused by a validator of schema 1.3.x to 1.5.x. This is the precedent of SREP 57,
whose generated marker ids are "accepted in every version" (schema 1.4.0): a newer validator accepts what an older
one refused, and no valid document changes. An author who needs an older validator to accept the document keeps
declaring 1.3.

**Interaction with the drafts.** With SREP 76's and SREP 80's amended BH1 and VOX1, every 1.3 construct is admitted
in every later version. Without those amendments, SREP 83 alone still admits SREP 40's constructs in 1.4 and later.

The 28 cases are in `conformance/srep_cases/srep-0083.json`, written by `conformance/tools/srep83_cases.py`
from existing kit cases (SREP 40's, one per gate, and one case of each of the drafts SREPs 77 to 80 that puts its
syntax on a gated element) with only `scene/@version` changed; GEO1, which no SREP 40 kit case exercises, has a globe
with elevation written by the tool. They are findings cases. sr-core's schema up to 1.5.0 has no version 1.6, so no
case uses it. `tests/test_srep_0083.py` applies the diff above to the 1.5.0 Schematron and, by content, to the files
with the drafts SREPs 76 to 81, and checks that:

- each case has its verdict; without SREP 83 the 1.4 and 1.5 cases are refused by their gate;
- the diff changes exactly the seven gates;
- no other kit case changes verdict, and every 1.3 kit case keeps its verdict in 1.0 to 1.5 as described under
  Backwards compatibility.

## Open issues

- **Messages.** The gates' messages now say "1.3 or later". The drafts SREPs 66 to 75 word theirs "needs
  version=\"1.6\"". A single wording for every version gate is left to the editor.
- **Release of the 1.4 and 1.5 documents.** Documents of 1.4 and 1.5 that use these constructs become valid only with
  the release that takes this SREP (1.6). Whether that release note should name them, as 1.4.0 named SREP 57's
  change, is the editor's choice.
