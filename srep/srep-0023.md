# SREP 23 — Draw corner radii on rect shapes

## Abstract

`radius` and `cornerRadii` are declared on every `shape`, but D27 gives corner radii only to
`rounded-rect`, and the engines disagree about a `rect` that sets them: the reference implementation rounds
its corners and the C engine draws it square. This SREP rules that a `rect` honours `radius` and
`cornerRadii` exactly as a `rounded-rect` does, and that a `rect` whose radii are all 0 is still drawn
exactly. It amends D26 and D27 and changes no schema.

## Motivation

- **The engines disagree.** For `<shape shape="rect" radius="8">`:
  - the reference implementation rounds the corners: `rect` and `rounded-rect` share one branch
    (`sr-gpu/src/vector.rs`, `"rect" | "rounded-rect"`);
  - the C engine draws the rect exactly: its rounded outline is built only for `rounded-rect`
    (`src/xml11/tr_core.c`, `outline_shape`, as read on 2026-09-30).

  The same document has round corners on one engine and square ones on another, and nothing reports it.
- **Scenes rely on the rounding.** 59 shapes in the local scenes set `radius` or `cornerRadii` on
  `shape="rect"`, all in production video projects: 47 in one, 6 in each of two others. They were made and
  reviewed on the reference implementation.
- **The definitions are silent, not contrary.** D27 defines `rounded-rect`'s corners and says nothing of a
  `rect` with radii; D26 says a stroked rect draws "the rect exactly". The XSD declares both attributes on
  `shapeType` for every shape kind, with no restriction.

## Specification

### Semantics

1. A `shape="rect"` whose `radius` is greater than 0, or whose `cornerRadii` has any radius greater than 0,
   MUST be drawn with the outline D27 gives `rounded-rect` for the same attributes: circular corners of
   `radius`, or of `cornerRadii` (top-left, top-right, bottom-right, bottom-left), each corner in 16 steps,
   every radius scaled by the least ratio when two radii on a side exceed it (CSS `border-radius`).
2. A `rect` whose radii are all 0 (the default) is drawn exactly, as before.
3. **Amendments**, applied to DEFINITIONS.md when this SREP is accepted:
   - D27, the `rounded-rect` item, gains: "A `rect` with a nonzero `radius` or `cornerRadii` has this
     outline too."
   - D26, *Rects and ellipses*, reads "the rect exactly, unless it has corner radii (D27)".

### Defaults and the neutral case

`radius` defaults to 0 and `cornerRadii` is absent by default, so a `rect` that sets neither is drawn exactly
as before on every engine.

## Rationale

The order of evidence in SREP 0:

1. **The baseline.** The reference implementation draws the corners. A declared default of 0 keeps every
   `rect` that does not ask for radii exact, so no document changes unless it asked.
2. **The author's intent is unambiguous.** A document that sets `radius` on a rect wants rounded corners;
   there is nothing else the attribute could mean.
3. **External precedent.** CSS `border-radius` applies to any box; SVG `<rect>` rounds with `rx`/`ry`.
   Neither has a separate rounded-rectangle primitive.
4. **Scenes in use.** 59 shapes in three production projects rely on it, and keep their look.

`rounded-rect` stays valid and means the same thing; it becomes an alias for a `rect` with radii.

## Rejected alternatives

- **Keep D27 as read strictly (radii ignored on `rect`), and change the reference implementation.** It would
  square the corners of 59 shapes in three production projects on their next render, without an error or
  a warning.
- **Reject `radius` on `rect` in Schematron.** It would make 59 shapes' documents invalid for asking for
  something every renderer can draw.
- **Report it as an inert attribute ([SREP 18](srep-0018.md)).** An attribute the reference implementation
  draws is not inert.

## Backwards compatibility

A Semantics ruling on a silent construct. No document changes validity. Documents render as before on the
reference implementation; on the C engine, rects with radii change from square to rounded corners, matching
the renders they were made with.
