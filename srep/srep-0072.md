# SREP 72 — Add pixel-exact options: working precision, shader content coordinates, edge blending and supersampling

## Abstract

This SREP adds four small options for authors who must match a reference picture pixel for pixel.

1. **`project/@precision="f32"`** makes every working texture 32-bit float. Today they are 16-bit float.
2. **Two built-in shader inputs, `sr_PixelCoord` and `sr_ContentRect`.** They give a shader effect its position
   relative to the node's content box, with no hidden margin. Today a shader's tile starts 2 to 3 px outside the
   content, and nothing tells the shader where the content is.
3. **A per-node `edgeBlend`** (`linear` or `encoded`) chooses the space in which that node's antialiased edges and
   opacity mix with what lies beneath. Today only `project/@linearLight` exists, for the whole document.
4. **`project/@supersample` with `supersampleFilter`** (`box` or `lanczos3`) renders N times larger and filters
   down with a stated kernel.

All defaults render as today.

## Motivation

**The owner's atlas test (2026-10-09, not published).** "The undocumented 3 px margin and the linear blending cost
me 20 to 30 dB." The f16 working textures and the engine's own text rasteriser "prevent exact equality". The owner's
proposal asked for `precision="f32"`, `sr_PixelCoord` and `sr_ContentRect`, `edgeBlend="encoded"` per node, and
`supersample="3" filter="lanczos3|box"`. The plan (B2) keeps those four. It drops the FreeType fallback and the CPU
reference renderer (Rejected alternatives).

**Checked in the reference** (`rs-scene-render` commit `c09b58a`):

- **Working textures.**
  - `pub const FORMAT: wgpu::TextureFormat = wgpu::TextureFormat::Rgba16Float;` (`crates/sr-gpu/src/resources.rs:13`)
    is a compile-time constant. There is no option.
  - `Rgba32Float` appears only in the 3D G-buffer and depth paths (`gpu.rs:482`, `three.rs:807`).
- **The margin.** The tile a shader effect sees is computed in `crates/sr-gpu/src/render_fx.rs:933-957`. The code
  comment reads: "custom shaders see tile: the layer's pixels with a 2 px margin".
  - The tile is `[floor(x0 − reach − 2), floor(y0 − reach − 2), ceil(x1 + reach + 2), ceil(y1 + reach + 2)]`, clamped
    to 64 px beyond the frame. Here (x0, y0)–(x1, y1) is the node's transformed box and `reach` its stroke or
    padding reach.
  - With no reach, the content's top-left therefore sits **2 + frac(x0) px** inside the tile: 2 px for a box on whole
    pixels, up to 3 px otherwise. This confirms the owner's measurement of about 3 px.
  - That holds for a "bounded" node, a `layer` or `shape` without children, a stencil blend or a reshaping modifier
    (`render_fx.rs:906-913`). Any other node's tile is the whole frame (`render_fx.rs:919`).
- **Shader inputs.** A shader receives the tile's size and origin (`iResolution`/`iOffset`/`iFrameResolution`,
  `resolution`/`tileOffset`/`frameResolution`, ISF `RENDERSIZE`; `crates/sr-gpu/src/shader.rs:793-822`, 907). It
  receives no content rectangle.
- **Blending.** `project/@linearLight` sets the working space as linear or not for the whole document
  (`crates/sr-gpu/src/color.rs:394`). No node can override it.
  - **Not traced:** exactly which compositing steps `linearLight` switches.
- **Antialiasing.** There is no 2D supersampling control. `project/@antialias3d` (1–4) is for 3D only, and 2D
  vectors are antialiased analytically by the tile rasteriser (`crates/sr-gpu/src/raster.rs`).

## Specification

### Syntax

```xml
<!-- projectType gains -->
<xs:attribute name="precision" default="f16">
  <xs:annotation><xs:documentation>Working textures (offscreens, effect passes, persistent buffers, the frame): f16 or f32 per channel. SREP 72.</xs:documentation></xs:annotation>
  <xs:simpleType><xs:restriction base="xs:string"><xs:enumeration value="f16"/><xs:enumeration value="f32"/></xs:restriction></xs:simpleType>
</xs:attribute>
<xs:attribute name="supersample" default="1">
  <xs:simpleType><xs:restriction base="xs:positiveInteger"><xs:maxInclusive value="4"/></xs:restriction></xs:simpleType>
</xs:attribute>
<xs:attribute name="supersampleFilter" default="box">
  <xs:simpleType><xs:restriction base="xs:string"><xs:enumeration value="box"/><xs:enumeration value="lanczos3"/></xs:restriction></xs:simpleType>
</xs:attribute>

<!-- nodeCoreAttributes (every node) gains -->
<xs:attribute name="edgeBlend" default="inherit">
  <xs:simpleType><xs:restriction base="xs:string">
    <xs:enumeration value="inherit"/><xs:enumeration value="linear"/><xs:enumeration value="encoded"/>
  </xs:restriction></xs:simpleType>
</xs:attribute>
```

Schematron: none. These are attributes with neutral defaults, accepted in every version under SREP 4.

The name `precision` is already used by an attribute of another type in schema 1.5.0 (a `positiveDecimal`,
default 0.7071). Attribute names are local to their element, so the two do not conflict.

### Semantics

**1. `precision`.** With `f32`, every 2D working texture stores at least IEEE 754 binary32 per channel. These are
the textures of:

- effects: effect intermediates and ISF pass targets, including `FLOAT` and `PERSISTENT` targets;
- the 2D rasteriser and the compositor: node offscreens and the frame before output encoding;
- particles;
- video: the working-space textures that decoded frames are converted into;
- the pool of offscreen textures that these share.

With `f16` (the default), they store at least binary16, as today.

**Scope.** The 3D renderer's internal buffers (G-buffer, lighting, depth of field, post) keep their own formats,
which are f16 today, whatever `precision` says. A 3D layer is converted to f32 when it enters the 2D compositor.
When `precision="f32"` and the document has 3D content (an `object3D`, `particles3D` or `ocean`), an
engine MUST report the information finding **PREC1** ("3D internal buffers stay f16"), in the validator and in the
render report (SREP 18). The document stays valid.

**Device features.** f32 working textures must be blendable and filterable. An engine whose device lacks either
capability (in WebGPU terms, `float32-blendable` and `float32-filterable`; in wgpu, `FLOAT32_BLENDABLE` and
`FLOAT32_FILTERABLE`) MUST fail the render with the error **PREC10**, naming the missing feature. It MUST NOT fall
back to f16 silently.

**2. `sr_PixelCoord` and `sr_ContentRect`.** Every `shader` effect receives two inputs, in every program form
(Shadertoy, plain and ISF):

- `uniform vec4 sr_ContentRect`: (left, top, width, height) of the node's content box, in tile pixels, measured
  from the tile's top-left corner with +y down. The values are exact, not rounded. The content box is the node's
  box transformed to target pixels: its local `width` × `height`, or the bounds of its drawing for a node without
  a size. For a rotated or skewed node it is the axis-aligned bounds of that box.
- `vec2 sr_PixelCoord`: for the fragment whose pixel centre is at tile pixel (i + 0.5, j + 0.5) from the top-left,
  `sr_PixelCoord = (i + 0.5 − left, j + 0.5 − top)`.

So `sr_PixelCoord` is (0.5, 0.5) at the centre of the content's first pixel when the content starts on a whole
pixel, and its x is in [0, width) across the content. Whatever margin the tile has, the shader can locate the
content exactly. The tile's margin itself (2 px plus outward rounding, Motivation) becomes documented behaviour:
the annotation of `effectType` states it.

**3. `edgeBlend`.** The value selects the space in which this node's own pixels composite onto the backdrop. A
pixel has colour C, and coverage × opacity α. Coverage is the area fraction of the pixel covered by the node's
geometry.

- `linear`: `out = α·C + (1 − α)·B` in the linear working space.
- `encoded`: `out_e = α·C_e + (1 − α)·B_e`, where the `_e` values are display-encoded (the sRGB transfer function of
  CONVENTIONS 1.4). The result is decoded back into the working space.
- `inherit`: `linear` when `project/@linearLight` is true, `encoded` when it is false.

The value applies to the node's own drawing. A group's `edgeBlend` applies when its offscreen composites (an
isolated group) and is not inherited by its children.

**4. Supersampling.**

- **Rendering.** With `supersample = n > 1`, the frame is rendered at n × width by n × height, with every length
  scaled by n, as by a render scale. The output pixel i (in x, and likewise in y) is then a separable weighted mean
  of the samples. Sample k has its centre at `(k + 0.5)/n` output pixels.

      out(i) = Σ_k w(s_k − (i + 0.5)) · v_k / Σ_k w(s_k − (i + 0.5))

- **Kernels.**
  - `box`: w(x) = 1 for the samples inside pixel i (⌊s_k⌋ = i), and 0 otherwise.
  - `lanczos3`: `w(x) = sinc(x)·sinc(x/3)` for |x| < 3 and 0 otherwise, with `sinc(x) = sin(πx)/(πx)` and
    `sinc(0) = 1`. Here x is in output pixels.
- **Edges and range.** At the frame's edges, the sum runs over existing samples only (the weights renormalise).
  The mean is taken in the working space before output encoding. The result is clamped to [0, 1] per channel,
  removing Lanczos overshoot. Alpha is filtered like the colour channels.
- **`n = 1`.** This is the current rendering, and `supersampleFilter` is not read.

`supersample` multiplies the render cost by about n². It composes with `antialias3d`, which then applies within
each sample.

### Errors

| Code | When | Stage |
|---|---|---|
| PREC1 | information: `precision="f32"` in a document with 3D content, whose internal buffers stay f16 | validation and render report |
| PREC10 | `precision="f32"` on a device without float32 blending or filtering | render |

### Defaults and the neutral case

- `precision="f16"`: today's format.
- `edgeBlend="inherit"`: the project's `linearLight`, as today.
- `supersample="1"`: no supersampling.
- The two shader inputs are new names. A shader that does not read them is unaffected. A shader that already
  declares its own variable named `sr_PixelCoord` or `sr_ContentRect` would collide. The `sr_` prefix is reserved
  for the engine from this SREP on (Backwards compatibility).

## Rationale

- **Coordinates, not removal of the margin.** Removing the margin would change every existing shader effect's
  picture: their `uv` and `resolution` depend on the tile. Giving the shader the content rectangle keeps old
  pictures and lets new shaders be exact.
- **Per-node edge blending.** A reference picture made by a tool that blends in encoded values can then be matched
  node by node, without moving the whole document out of linear light.
- **Box and Lanczos-3.** The box is the exact area average. Lanczos-3 is the usual sharp downsampling kernel. Both
  are closed-form, so an engine can match them exactly.

## Rejected alternatives

- **A CPU reference renderer:** an XL task, which the plan defers to its own SREP after phase 2. llvmpipe already
  shows that CPU renders differ across CPU models (the plan, A7).
- **A FreeType text fallback with configurable hinting:** it is in the owner's proposal but not in the plan's B2.
  It would change text layout and needs its own SREP.
- **`precision="f32"` per node:** precision is a property of the textures that nodes share. Mixing per node would
  convert at every boundary.

## Backwards compatibility

The change is MINOR, with neutral defaults. The reserved `sr_` prefix in shader sources could, in principle, collide
with an existing shader's own identifier of that name. No such shader is known. An engine SHOULD report such a
collision as a shader compile error naming the reserved identifier.

## Conformance

The cases are in `conformance/srep_cases/srep-0072.json`. They are written, with the shaders
`srep_cases/assets/srep72-*.fs`, by `conformance/tools/srep72_cases.py`. All are pending.

| Case | Checks | Tolerance |
|---|---|---|
| `srep-0072-precision-f32` | 2049 survives a FLOAT pass target (binary16 cannot hold it: its spacing is 2 there) (1) | 2 px |
| `srep-0072-precision-3d-note` | `precision="f32"` with an `object3D`: valid, with the finding PREC1 (1) | exact |
| `srep-0072-content-rect-stripe`, `-fractional` | a shader paints the first 10 px of the content box using `sr_PixelCoord`, at whole and fractional positions (2) | 2 px |
| `srep-0072-edge-blend-linear`, `-encoded`, `-inherit` | a half-covered column is 187.5 (linear) or 127.5 (encoded); `linear` overrides `linearLight="false"` (3) | 3 code values |
| `srep-0072-supersample-box`, `-lanczos3` | eight columns across a pixel-aligned step edge at n = 2 (4) | 3 code values |

**Assumption, not checked:** the edge cases assume that the rasteriser's coverage is the exact area fraction (0.5 for
a half-covered pixel). If the reference's analytic coverage differs, those expected values need its coverage
function.

## Open issues

- How `edgeBlend` interacts with a node's blend modes other than `normal`. This draft defines it for `normal` only.
- Whether `sr_ContentRect` should also give the rotated box (a 2×3 matrix) for rotated nodes.
