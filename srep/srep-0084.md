# SREP 84 — Boolean and integer attributes are tested by value, not by spelling

## Abstract

Eight Schematron rules of sr-core 1.5.0 (C15, C43, R15, R48-from, R48-to, C80, VOL5, GEO2) and three of the draft
SREP 78 (PYRO9, PYRO10, PYRO11) compare an `xs:boolean` or an `xs:integer` attribute with one spelling of its value:
`@reverse='false'`, `@loop='0'`, `@alpha='true'`, `@threeD='true'`, `@hasAudio='true' or @hasAudio='1'`, or a number
that XPath 1.0 cannot read when it has a leading `+`. The XSD accepts other spellings of the same values (`1`, `0`,
`" true "`, `"+0"`, `"00"`), so a rule is bypassed (it does not refuse a document that it should) or misfires (it
refuses one that it should not). This SREP rewrites each comparison to test the value: a boolean is true when
`normalize-space(@a)='true' or normalize-space(@a)='1'`, the form the draft SREP 76 already uses for BH5 to BH8; an
integer is read as `number(substring(normalize-space(@a),1+number(starts-with(normalize-space(@a),'+'))))`, the form
the 1.5.0 Schematron already uses for VOL6. No kit case outside this SREP changes verdict. The XSD does not change.

## Motivation

- **The lexical forms are values of the XSD.** `xs:boolean` has the literals `true`, `false`, `1` and `0` (XML Schema
  1.0 Part 2, 3.2.2), and `xs:integer` (3.3.13), from which `xs:nonNegativeInteger` (3.3.20) and
  `xs:positiveInteger` (3.3.25) derive, is "an optional sign followed by a finite-length sequence of decimal digits".
  Both collapse whitespace (4.3.6), so `" true "` and `" 0 "` are valid too. A document that writes `reverse="0"`,
  `threeD="1"` or `loop="+0"` passes the XSD with the value false, true, 0.
- **The reference reads the value.** The reference engine's model reads a boolean as true for `true` and `1` and false
  for `false` and `0` after trimming whitespace, and an integer with an optional sign (`rs-scene-render`,
  `crates/sr-model/src/parse.rs`, `ParseValue for bool` and `int_parse!`; `crates/sr-model/src/xsd/mod.rs`,
  `parse_xsd_integer`; at `prep/srep-83-version-gates` 6f9d13c0). It renders `threeD="1"` as a 2.5D node and
  `alpha="1"` as an output with alpha, while R48 and C43 test only `'true'`.
- **XPath 1.0 compares strings as strings and reads no `+`.** `@a='true'` is a string comparison, so `"1"` and
  `" true "` are not equal to it. `number()` converts "optional whitespace followed by an optional minus sign
  followed by a Number followed by whitespace", "any other string is converted to NaN" (XPath 1.0, 4.4), so `"+0"`
  is NaN and `@from[. != 0]` holds for it. Whitespace and leading zeros are read correctly by `number()`; the sign is
  not.
- **The drafts already did this for their own rules.** The drafts SREP 76 (BH5 to BH8, its third amendment) and
  SREP 77 (CRT11, CRT12) were amended on 2026-10-10 to read every form of `camera/@geodesics` and `crater/@mantle`.
  The rules of the accepted SREPs and of SREP 78 kept the literal tests; this SREP is the inventory and the change
  for them.

### Semantics

1. **Booleans.** A rule that reads an `xs:boolean` attribute `a` MUST treat it as true when its value, whitespace
   collapsed, is `true` or `1`, and as false when it is `false` or `0`; an absent attribute is neither, and each rule
   keeps what it did for an absent attribute. In XPath 1.0 the test is `normalize-space(@a)='true' or
   normalize-space(@a)='1'` (and `='false' or ='0'` for false). `normalize-space` strips leading and trailing
   whitespace and collapses the rest (XPath 1.0, 4.2), as the XSD's `collapse` does for `xs:boolean`.
2. **Integers.** A rule that reads an `xs:integer` attribute (or one derived from it) MUST read its value, whatever its
   sign, leading zeros or whitespace. In XPath 1.0 that is
   `number(substring(normalize-space(@a),1+number(starts-with(normalize-space(@a),'+'))))`: a leading `+`, which
   `number()` refuses, is removed; `number()` reads leading zeros, a `-` and the surrounding whitespace. GEO2 tests
   membership in the powers of two from 1 to 4096 by the string of that number: `string()` writes an integer "with no
   decimal point and no leading zeros" (XPath 1.0, 4.2), so `contains(' 1 2 4 … 4096 ', concat(' ', n, ' '))` holds
   exactly when `n` is one of them, and is false for NaN.
3. **Rule by rule.** C15 accepts a `timeRemap` beside `reverse` false in any form and `loop` 0 in any form; C43
   refuses `alpha` true in any form with a codec that carries no alpha; R15 accepts a video whose `hasAudio` is true in
   any form; R48-from and R48-to refuse a target that is, or is inside, a node with `threeD` true in any form; C80
   refuses a points child beside a `from` other than 0 or a `step` other than 1, by value; VOL5 refuses `blackbody`
   true in any form without a temperature grid (or a pyro); GEO2 accepts a power of two in any form; PYRO9 and PYRO10
   read `follow` true in any form; PYRO11 reads `followMargin` by value. Nothing else in these rules changes: their
   contexts, messages and the parts that read other attributes are as before.
4. **Native validators.** A validator that mirrors the Schematron in its own code MUST make the same change. The
   reference does (Engine impact).

### Errors and warnings

The rule ids, contexts and messages are unchanged. What each refuses changes only for the documents that write one of
these attributes in a form other than the one compared before (Backwards compatibility). No warning is added. The
reference's warning W02 (a pyro source near an open face, SREP 40) also reads `pyro/@follow`; the reference reads it
by value as well (Engine impact).

### Defaults and the neutral case

No default changes. A document that writes these attributes as `true`, `false` and digits without sign or padding,
which is how every kit case and every corpus document of the reference wrote them before this SREP, gets the verdict
it had.

## Rationale

- **The value is what the XSD defines and what renders.** A rule that guards a rendering choice has to fire on the
  documents that make that choice. Testing one spelling ties the verdict to how the author typed the value, which no
  other part of the format does.
- **The form of the drafts.** `normalize-space(@a)='true' or normalize-space(@a)='1'` is the form of the draft SREP
  76's BH5 to BH8 and SREP 77's CRT11 and CRT12, and the `+` form for integers is that of 1.5.0's own VOL6. One form
  for each type keeps the rules alike and the native mirrors simple (the reference has one function for each).
- **XPath 1.0.** The Schematron's `queryBinding` is `xslt` (XSLT 1.0, XPath 1.0), so sequence comparisons such as
  `normalize-space(@a)=('true','1')` (XPath 2.0) are not available; the disjunction is the XPath 1.0 form of it.

## Rejected alternatives

- **Restrict the XSD to `true` and `false`.** A pattern facet on these attributes would refuse `1`, `0` and padded
  forms. Every document that writes them, valid today, would become invalid: Breaking under SREP 4. It would also
  differ from every other `xs:boolean` in the schema.
- **Compare with `boolean()` or `number()` of the attribute.** `boolean(@a)` is true for any non-empty string,
  `"false"` included; `number(@a)=1` is NaN for `"true"`. Neither reads both forms.
- **Leave the misfires.** They refuse valid documents that a renderer can render; the bypasses accept documents whose
  rendering the rule exists to prevent (a connector to a 2.5D node, an output that asks for alpha it cannot carry,
  black-body light with no temperature).

## Backwards compatibility

**Class.** Bug fix of the rules under SREP 4, with a verdict change in both directions for the forms listed in the
inventory: documents refused by a misfire become valid (C15, R15, C80, GEO2, PYRO10, PYRO11), and documents that a
bypass let through become invalid (C43, R48-from, R48-to, VOL5, PYRO9). The second kind is a document that asked for
what the rule forbids, in a spelling the rule did not read; it was invalid by the rule's own meaning. No document
that writes these attributes as `true`, `false` or unsigned, unpadded digits changes verdict.

**Do existing verdicts change? Not in the kit.** `tests/test_srep_0084.py` validates every one of the 453 kit case
files outside this SREP with and without SREP 84, against the 1.5.0 files and against the files with the drafts SREPs
76 to 81 and 83: none changes verdict. The reference's corpus gives the same answer for its documents written before
this SREP (Engine impact).

**Release.** The change of the 1.5.0 rules can be taken in the next release on its own; the change of PYRO9 to
PYRO11 belongs to the release that takes SREP 78.

## Open issues

- **Numbers of type `xs:double`.** The same `number()` reading is used for `xs:double` attributes (C13, C14, C15's
  `@speed`, C37, C38, C44, C52, C54, C56, OCN3, P3D3, PYRO2, VOL4 and others in 1.5.0; OCN14 in the draft SREP 79 uses
  `translate(…,'+','')`). `"+1"` is NaN there too, and so are exponent forms such as `"1e0"` in XPath 1.0 (libxml2,
  which the kit's tests use, reads exponents; the reference's mirror does the same, `xpath_number` in
  `crates/sr-model/src/rules.rs`). The `+` form above fixes the sign but not the exponent for a strict XPath 1.0
  processor. This SREP covers booleans and integers, whose lexical forms the `+` form reads completely; doubles need
  their own decision.
- **ITR1 (draft SREP 67).** `number(@checkEvery) <= number(@steps)` should take the integer form above. SREP 67 is on
  `srep/drafts-2026-10`, outside this stack; its own draft should take it.
- **Messages.** The messages still quote one spelling (`alpha="true"`, `hasAudio="true"`). They describe the value, and
  are left as they are.
