# SREP 0 — SREP purpose and process

## Abstract

A **Scene Render Enhancement Proposal** (SREP) is a short design document proposing one change to the
scene-render format. A change can be to the XSD, to the Schematron rules, or to what the values in a document
mean. The SREP records the proposal, the evidence for it, how conformance to it is tested, and the decision.

This document defines how SREPs are written, reviewed and decided. [srep-template.md](srep-template.md) is the
form to copy.

The process borrows from two existing ones:

- **Python's PEP 1 and PEP 12:** numbered documents, a fixed form, statuses, and one person who decides.
- **The Java Community Process:** a change is finished only when it has a reference implementation and passes
  a compatibility kit that every implementation must pass.

## Baseline

The scene format as implemented by **Rust** (`rs-scene-render`) is the baseline. Specifically:

- `schema/scene-render-1.1.xsd` and `schema/scene-render-1.1.sch` at `origin/main` `5e8ff6e`, with SHA-256
  `15861a8f…642273` and `d56520fb…c33fad`, imported unchanged into `sr-core/schema/` (later changes are listed
  in `schema/README.md`);
- the rendered behaviour of that engine where the schema is silent.

**Canonical source.** From the import on, `sr-core/schema/` holds the one canonical copy of the XSD and the
Schematron, with their hashes in `schema/SHA256SUMS`. Every engine, Rust included, vendors those exact files.
A change to `schema/` lands only with the SREP that accepts it, and in the same change `docs/schema/`, the HTML
reference generated by `sr-schemadoc`, is regenerated; the sr-core tests fail when it is stale.

Everything in the baseline is the standard as it stands, without needing an SREP. Any change from the
baseline needs one, whether the change is made in Rust or in another engine. Where another engine differs from
the baseline, that engine is wrong unless an SREP says otherwise.

Formats that sit beside the scene format, such as the package format of [SREP 1](srep-0001.md), follow the
same process. Their reference implementation is named in their own SREP rather than being Rust.

## Roles

| Role | PEP / JCP analogue | Who | Does |
|---|---|---|---|
| **Author** | PEP author / spec lead | anyone, human or agent session | writes the SREP, answers review, keeps it current |
| **Schema editor** | BDFL-Delegate / Executive Committee | the repository owner | assigns numbers; decides Accepted, Rejected and Deferred; releases schema versions |
| **Reference implementation** | JCP RI | Rust | implements an SREP first; its render is the reference picture |
| **Implementers** | JCP licensees | C, Python and JavaScript engines | implement Accepted SREPs; report the SREP's status in their engine |
| **Compatibility kit** | JCP TCK | the conformance cases (`scene-render-conformance/cases/`, `run.py`) | decides whether an engine conforms |

Only the schema editor's recorded decision changes an SREP's status. Agreement among agent sessions, and
messages relayed between them, are input to that decision, not the decision itself.

## When an SREP is needed

| Change | SREP |
|---|---|
| New element, attribute, enumeration value, asset kind or Schematron rule | Yes: **Standards** |
| New or changed default | Yes: **Standards** |
| Defining what a silent construct means (units, axes, order of operations, formulas) | Yes: **Semantics** |
| Changing baseline behaviour, including fixing a Rust bug that existing scenes rely on | Yes: **Semantics** |
| Changing this process, versioning or the compatibility-kit thresholds | Yes: **Process** |
| Guides, surveys of options, gap reports | Optional: **Informational** |
| An engine that differs from the baseline or from an accepted SREP | No: fix the engine and add a case |
| Performance, command-line flags, engine-only options | No |

When in doubt, write one. A two-paragraph SREP is fine.

## Lifecycle

```
 idea ─► Draft ─► Review ─► Accepted ─► Final
                    │          │          │
                    │          └► Deferred └► Superseded
                    ├► Rejected
                    └► Withdrawn (by the author, from any state before Final)
```

1. **Idea.** Optional. Before writing, the author may open an issue to ask whether the idea is wanted.
2. **Draft.** The author copies the template to `srep/srep-0000-<slug>.md` and fills in at least Abstract,
   Motivation and Specification. The editor checks that the form is complete, assigns a number, and renames
   the file to `srep-NNNN.md`.
3. **Review.** Before this, the SREP needs:
   - a **reference implementation** in Rust, on a branch;
   - at least one **compatibility-kit case**.

   The review period is at least 7 days. Implementers state in the SREP's Engine impact table what the change
   costs them, and they may object there.
4. **Accepted.** The editor decides, and records the date and reason under **Resolution**.
   - Rust's reference implementation merges.
   - The change enters the target schema version.
   - The other engines may implement it.
5. **Final.** Every engine passes the SREP's cases, and the schema version carrying it is released.
   Implementers that can't pass yet are marked `pending` in the SREP, and it stays Accepted until none are.
6. **Deferred, Rejected, Withdrawn.** The SREP is kept, with its reasons, so the argument doesn't have to
   be made again.
7. **Superseded.** A later Final SREP names this one in `Replaces`.

SREP numbers are never reused, and SREPs are never deleted.

**Changes after acceptance.**
- A correction that doesn't change rendered behaviour is an erratum: a dated line under **History**.
- A change in behaviour needs a new SREP that supersedes the old one.

## How a proposal is argued

Evidence carries weight in this order:

1. **The baseline:** its conventions (pixels, +y down, clockwise degrees, straight alpha, determinism), its
   declared defaults, and its documentation. A proposal that makes a declared default absurd is wrong.
2. **Accepted and Final SREPs.**
3. **External precedent, with section references:** SVG 2, CSS Compositing, CSS Color, glTF 2.0, OpenUSD,
   and After Effects for motion-graphics behaviour.
4. **Scenes in use:** the videos and packages that the change would affect, and how their pictures change.

Every SREP meets four design rules, or says under **Backwards compatibility** why it can't:

- **Neutral defaults.** Omitting a new attribute renders exactly what the baseline rendered.
- **Determinism.** Every random, noise or generated value is an exactly specified function of
  `project/@seed`, the element's own seed and the frame time. External services are resolved from a declared
  cache whose content hash is part of the document.
- **One space.** Everything is in pixel space, with 3D extending 2D. Physics converts through
  `pixelsPerMeter`, and no second coordinate system is introduced.
- **Engine-neutral specification.** The Specification says what the picture is. How an engine computes it
  goes under Engine impact.

## Versioning

The schema follows Semantic Versioning, under the rules of [SREP 4](srep-0004.md). In short:

- **The release version** is `xs:schema/@version`, MAJOR.MINOR.PATCH, tagged `schema-X.Y.Z`. The file names
  carry no version ([SREP 3](srep-0003.md)).
- **Documents** declare only MAJOR.MINOR (`<scene version="1.1">`). A PATCH release never changes what a
  document may or must say.
- **PATCH** covers documentation, messages and wording, with no change in what validates or how it renders.
  This is the usual case.
- **MINOR** adds; it doesn't break. Every document valid under 1.N stays valid under 1.N+1 and renders the
  same.
  - New elements, sections and asset kinds require the new `version="1.N"` on the document, and the
    Schematron enforces this.
  - New attributes with neutral defaults are accepted in every version.
- **MAJOR** breaks. It needs a Process SREP listing every breaking change, and a migration tool.
- **Accumulating changes.** SREPs record their class in `schema/CHANGELOG.md` when they land.
  `tools/release.py` computes the one bump that is due when a release is cut, so accepted SREPs accumulate
  into a single release.
- **Release.** A version is released when every SREP targeting it is Final or has moved to a later version.
  Engines vendor the tagged files, whose hashes are in `schema/SHA256SUMS`, and the generated `docs/schema/`
  reference is published beside them.

## Experimental syntax

An engine may try syntax before its SREP is accepted, but only under the namespace
`urn:scene-render:x-<engine>`, and only with an SREP in Draft or Review.

Engines that don't recognise an `x-` construct ignore it with a warning. They never reject the document.

Once the SREP is accepted, the syntax moves into the standard namespace. The engine keeps reading the `x-`
form for one minor version.

## Compatibility kit

- **Case names.** Each SREP's cases are in `scene-render-conformance/cases/srep-NNNN-<slug>/`.
- **Coverage.** Every normative sentence in its Specification is covered by at least one case.
- **Passing a case** means both:
  - the case's own measurements (positions, colours, edge shifts, event times) are within tolerance;
  - the render matches Rust's reference render at 40 dB PSNR or better, unless the case states another
    tolerance.

## Form and numbering

- **Form.** Markdown, with the header block and sections of [srep-template.md](srep-template.md), in that
  order. A section that doesn't apply says "None."
  - Normative words (MUST, SHOULD, MAY; RFC 2119) appear only in **Specification**.
  - Required header fields: `SREP`, `Title`, `Author`, `Status`, `Type`, `Created`, `Schema-Version`.
- **Numbering.** SREP 0 is this process. Other numbers are assigned in order of submission, whatever the
  type.
- **Index.** `srep/index.md` lists each SREP's number, title, type, status and target version.
