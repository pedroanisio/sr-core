# SREP 66 — Add `<program>`: deterministic WebAssembly generators

## Abstract

A new element, `<program>`, runs a sandboxed WebAssembly module once, when the document is built, and puts
the scene-render XML that the module returns in its place. In the composition the module returns nodes, which the
program draws as a group. In `<parameters>` it returns data rows that `repeat/@over` can read. The module
can import only two things from the host: a seeded random number generator and reads of the program's parameters.
Its output is fixed by six determinism rules: canonical NaNs; no relaxed SIMD and no threads; a memory limit and
a fuel limit that the document states; no other imports; and a cache keyed by the module, its parameters and the
seeds. The document records the module's SHA-256. An author can then write a maze, a circle packing or an
L-system as a program, instead of as a Python script that writes the XML.

## Motivation

**The owner's 72-cell atlas test (2026-10-09, not published).** 18 of the 72 cells failed for one
reason: the format cannot compute geometry with loops. The cells are:

- recursive curves: L-system, dragon curve, Gosper curve;
- geometry algorithms: maze, wave function collapse, circle packing, Pythagoras tree, Collatz graph, force-directed graph;
- growth and point distribution: space colonisation, differential growth, stippling, Voronoi with Lloyd relaxation.

This is the largest group of missing cells in that test (11 cells needed accumulation, SREP 67, and 3 needed
procedural meshes, SREPs 70 and 71). The owner's test notes record the workaround: a Python script writes the XML
before rendering, so the algorithm lives outside the document and is not reproducible from it.

**What exists today**, checked in the Rust reference at `rs-scene-render` commit `c09b58a`:

- The expression language has no loops and no function definitions. The engine README states this as a design
  choice ("no loops or function definitions, so cost is bounded by length"). Its values are 64-bit floats
  (`crates/sr-eval/src/expr/vm.rs`, `Num(f64)`).
- `generator` already names something else: the procedural image asset (`generatorAssetType`, schema 1.5.0) with
  10 kinds: solid, gradient, noise, fractal-noise, cells, checkerboard, grid, stripes, film-grain, light-rays.
  This SREP therefore uses the name `program`.
- `repeat` places copies on a count, on data rows (`@over`) or on generated points (SREP 26). None of these
  can express a recursion or an algorithm with state.
- The engine has no WebAssembly runtime: `Cargo.lock` lists no `wasmtime`, `wasmi` or `wasmer`.

**Why the determinism rules are needed (measured).** The kit modules of this SREP were run in a WebAssembly
runtime that applies none of the rules: Node 24.18.0 (V8) on an x86-64 host, AMD Ryzen 7 170, 2026-10-09.

- `srep66-nan.wasm` divides 0 by 0 and tests whether the result has the bits of the positive canonical NaN
  (`0x7FF8000000000000`). It took the "no" branch, because x86 produces the negative quiet NaN `0xFFF8000000000000`.
  A module that hashes or branches on float bits would produce different documents on different hosts.
- `srep66-grow.wasm` grows its memory by 1100 pages (68.75 MiB). V8 allowed it. Under the 64 MiB default limit
  of this SREP the same call must fail with −1.
- V8 accepted the shared-memory and relaxed-SIMD modules (`srep66-shared.wasm`, `srep66-relaxed.wasm`) as valid.
  A host has to forbid these features explicitly; leaving them off is not enough.

### Semantics

**1. When it runs.** A program runs **once per document build**, before timing, layout and evaluation, and before
any frame is rendered. Its output does not depend on time. An author who wants animation writes it into
the emitted XML: keys, expressions and `animate` children, which the rest of the format then evaluates as usual.
A program has no access to the clock, the frame, the file system, the network, environment variables or other
nodes.

**2. The module interface.** `src` is resolved like any asset URI. The engine MUST compute the SHA-256 of the
file's bytes and fail with **PRG10** unless it equals `sha256`. The module:

- MUST be a valid WebAssembly module under the WebAssembly 3.0 core specification, excluding the proposals forbidden
  in Determinism 2.
- MUST export a memory named `memory`.
- MUST export a function `generate` of type `[] → [i64]`.

`generate` returns `(ptr << 32) | len`: `ptr` is the byte address in `memory` of the output and `len` its byte
length, both read as unsigned 32-bit integers. The output is the `len` bytes at `ptr`, read after `generate`
returns. A module that does not meet these requirements fails with **PRG11**.

**3. Imports.** The module MAY import only the following functions, from the module name `sr`:

| Import | Type | Returns |
|---|---|---|
| `rand_u64` | `[] → [i64]` | the next value of the program's generator (4), as the bits of an unsigned 64-bit integer |
| `rand_f64` | `[] → [f64]` | `(u >> 11) · 2⁻⁵³` for the next generator value `u`: a value in [0, 1) |
| `param_f64` | `[i32 i32 f64] → [f64]` | reads the parameter whose name is the UTF-8 string at (`ptr`, `len`). Returns its `value` parsed as an `xs:double`, or the third argument when there is no such parameter. A value that is not an `xs:double` fails with **PRG16**. |
| `param_str` | `[i32 i32 i32 i32] → [i32]` | arguments `(name_ptr, name_len, buf_ptr, buf_cap)`: writes at most `buf_cap` bytes of the parameter's UTF-8 `value` at `buf_ptr` and returns the value's full byte length, or −1 when there is no such parameter |

Any other import, including any WASI import, fails with **PRG11** when the module is loaded. `rand_u64` and
`rand_f64` draw from the same sequence. A memory access outside the module's memory in a host call fails with **PRG13**.

**4. The seeded generator.** Let `P` = `project/@seed` and `S` = `program/@seed`, as unsigned 64-bit integers.
`mix64` is the SplitMix64 finaliser:

    mix64(z) = z₃, where z₁ = (z ⊕ (z ≫ 30)) · 0xBF58476D1CE4E5B9, z₂ = (z₁ ⊕ (z₁ ≫ 27)) · 0x94D049BB133111EB, z₃ = z₂ ⊕ (z₂ ≫ 31)

All arithmetic is modulo 2⁶⁴. The state starts at `x₀ = mix64(P ⊕ mix64(S))`. The k-th call (k = 1, 2, …)
sets `x_k = x_{k−1} + 0x9E3779B97F4A7C15` and returns `mix64(x_k)`. This is SplitMix64 (Vigna) seeded with `x₀`.

**5. Output in the composition.** The output of a program in the composition MUST be UTF-8 text that is an
XML fragment: zero or more elements of `nodeChoice` (and whitespace between them), with no XML declaration, no
DOCTYPE, no processing instructions and no entity references other than the five predefined ones and character
references. The engine parses the fragment as if it were written in place as the program's children, after the
program's own `param` and `nodeBehaviour` children. It then validates the whole document again against the XSD
and the Schematron.

The program draws as a `group` with the program's `nodeAttributes`, `nodeBehaviour` and `blend` would draw:
its transform, timing, opacity, masks, matte and effects apply to the emitted nodes. Emitted ids share the
document's id space. An emitted id equal to any other id in the document is an error. So is output that is
not well-formed, is not valid, or has more than 1,000,000 elements. All of these fail with **PRG14**.

**6. Output in `parameters`.** The output of a program in `parameters` MUST be UTF-8 JSON in the form a `data`
element with `format="json"` accepts. The program is a data source with its own id, which `repeat/@over` can name
like a `data` element. Output that is not such JSON fails with **PRG14**.

**7. `outputSha256`.** When it is present, the engine MUST compute the SHA-256 of the output bytes (5 or 6) and
fail with **PRG15** unless it equals `outputSha256`. This lets an author pin a program's result across hosts and
engine versions.

### Determinism rules

These are the rules the plan requires (PLAN-ENGINE-2026-10-09, track B, B1). Each MUST hold.

1. **NaNs are canonicalised.** Every NaN that a floating-point instruction produces is the positive canonical NaN
   (`0x7FC00000` for f32, `0x7FF8000000000000` for f64). This is the deterministic profile of the WebAssembly 3.0
   specification, applied to NaNs.
2. **Relaxed SIMD and threads are forbidden.** A module that contains any relaxed SIMD instruction (the opcodes
   `0xFD 0x100` to `0xFD 0x113` of the relaxed SIMD proposal), a shared memory, or any atomic memory instruction
   (the prefix `0xFE`) fails with **PRG11** when it is loaded. It is never run. Fixed-width SIMD (`v128`) is allowed:
   it is deterministic apart from NaNs, which rule 1 covers.
3. **Fixed memory limit.** The module's memory MAY grow to at most `memoryLimit` × 16 pages of 64 KiB.
   - `memory.grow` returns −1 exactly when the new size would exceed that limit, and succeeds otherwise.
   - If the host cannot provide memory below the limit, the engine fails with **PRG13**. It never makes
     `memory.grow` return −1 for that reason. (Under the WebAssembly deterministic profile, `memory.grow` may still fail
     for want of resources. This rule removes that last source of non-determinism.)
   - A module whose declared minimum exceeds the limit fails with **PRG11**.
4. **Fuel limit.** Every executed instruction costs one unit of fuel, except `nop`, `drop`, `block`, `loop`,
   `unreachable`, `return`, `else` and `end`, which cost nothing. A `call` costs one unit, and the body of a host
   function (item 3 of Semantics) costs nothing. The fuel spent by a call of `generate` is the sum of these costs
   over the instructions executed. If it exceeds `fuel`, the engine fails with **PRG12** (fuel exhausted) and does
   not return partial output.
   - The engine MAY stop execution at any point after the spent fuel exceeds `fuel`; whether it fails depends only
     on the total.
   - These costs are the ones Wasmtime 41.0.4 charges (`wasmtime-internal-cranelift`, `func_environ.rs`,
     `fuel_before_op`). Wasmtime checks the remaining fuel only at function entries and loop headers. An engine
     using it gives the store `fuel + 1` units and reports PRG12 when execution traps for lack of fuel, or when it
     returns with no fuel left (`Store::get_fuel` saturates at 0, so 0 left means more than `fuel` was spent).
5. **No host imports except the seeded RNG and parameter reads.** The four imports of item 3 above are the whole
   interface. There is no clock, no file system, no network and no environment.
6. **Output cached by module, parameters and seed.** An engine MAY cache a program's output. When it does, the key
   MUST be the SHA-256 of the UTF-8 bytes of:

       "sr-program-1" NUL sha256 NUL decimal(P) NUL decimal(S) NUL decimal(fuel) NUL decimal(memoryLimit) NUL
       name₁ NUL value₁ NUL … nameₙ NUL valueₙ NUL

   where `sha256` is the module's lowercase hex SHA-256, the parameters are in ascending order of the UTF-8
   bytes of their names, and NUL is the byte 0x00. The output is a function of these inputs alone (rules 1–5),
   so a cached output is the output.

**Provenance.** The document records the module's SHA-256 (`sha256`, required). An engine's render report
(SREP 18) SHOULD list, for each program, `src`, `sha256`, the cache key of rule 6, the fuel spent and the output's SHA-256.

**Floating point.** Apart from NaN bit patterns, the WebAssembly arithmetic instructions are fully specified:
IEEE 754-2019 with round-to-nearest-even and no fused multiply-add unless the module itself uses one. Functions such as
`sin` are not instructions. A module that needs them carries its own implementation, compiled in. Its results therefore
depend only on the module's bytes.

### Errors

| Code | When | Stage |
|---|---|---|
| V12 | `program` in a document of version 1.0 to 1.5 | validation (Schematron) |
| PRG1 | two `param` children of one program with the same name | validation (Schematron) |
| PRG2 | `repeat/@over` names a program in the composition | validation (Schematron) |
| PRG10 | `src` cannot be read, or its SHA-256 differs from `sha256` | build |
| PRG11 | the module is invalid, lacks `memory` or `generate`, has another import, uses a forbidden feature, or declares a minimum memory above the limit | build (load) |
| PRG12 | fuel exhausted | build (run) |
| PRG13 | a trap (unreachable, out-of-bounds access, division by zero, stack exhaustion), or the host cannot provide memory below the limit | build (run) |
| PRG14 | the output is not UTF-8, not well-formed, invalid, collides with an id, exceeds 1,000,000 elements, or (data) is not the JSON a data source accepts | build (output) |
| PRG15 | the output's SHA-256 differs from `outputSha256` | build (output) |
| PRG16 | `param_f64` reads a value that is not an `xs:double` | build (run) |

Each build error stops the render with a non-zero exit and names the program's id and the code. None of them is a
warning.

### Defaults and the neutral case

A document without `program` is unaffected. The defaults: `seed` 0, `fuel` 10⁹ instructions, `memoryLimit`
64 MiB, no `outputSha256`.

## Rationale

- **WebAssembly, not a scripting language.** WebAssembly arithmetic is specified bit for bit apart from NaN payloads,
  which have a standard deterministic profile. A module carries its own maths library. Fuel and memory limits are
  standard runtime features (for example `consume_fuel` and `cranelift_nan_canonicalization` in Wasmtime's
  `Config`). Authors can compile from Rust, C, Zig or AssemblyScript. A scripting language would need its own
  numeric specification and sandbox.
- **XML fragments as output.** The output is checked against the same schema as hand-written XML, so a program
  can do nothing a document cannot. No second output model has to be specified.
- **Once per build.** This keeps the cost out of the frame loop and makes caching trivial. Programs that must step
  per frame are SREP 69 (`mode="step"`).
- **The document states the limits.** If they were engine settings, the same document could build on one host and fail on
  another.
- **SplitMix64.** It is already the mixer of the reference's own counter-based randomness (`mix64`,
  `crates/sr-eval/src/rng.rs`), and it is short enough to restate exactly.

## Rejected alternatives

- **Naming it `<generator>`**: that is the procedural image asset (10 kinds) of schema 1.5.0.
- **Adding loops and functions to the expression language**: the README calls their absence a design choice that
  bounds cost by length. Loops would need a fuel rule there too, and expressions run per frame.
- **A native `lsystem` node only**: it covers 3 of the 18 cells. SREP 70 keeps it as the fallback if this SREP is
  rejected or late.
- **An `emit` host import** (the module calls the host to emit each node): the plan allows only the RNG and
  parameter reads. Returning one buffer keeps the interface to four functions.
- **WASI**: it brings clocks, files and environment. Rule 5 forbids them.
- **Partial output when fuel runs out** (stop and keep what was emitted so far): partial output would depend
  on the exact fuel count. Rule 4 requires a hard failure.

## Backwards compatibility

The change is MINOR. It adds two elements under a version gate (V12) and changes nothing that existing documents
use. A valid 1.5 document stays valid and renders the same.

## Open issues

- **Stack depth.** A recursion deep enough to exhaust the stack traps (PRG13), but the depth at which it does
  depends on native frame sizes, which may differ between CPU architectures.
- **Id scoping.** Two programs that emit the same ids collide (PRG14). Prefixing emitted ids with the program's
  id (`p.g1`) would allow a program to be reused, but references inside the fragment would then need rewriting.
- **Default seed.** `S` defaults to 0. Other elements derive an absent seed from their id. Should a program do the same?
- **Text and fonts.** A program cannot measure text, because it has no host import for fonts. Layout that depends on
  text extents stays outside programs for now.
