# SREP 4 — Semantic versioning for sr-core, the schema and the package format

## Abstract

sr-core has three contracts, and each gets its own [Semantic Versioning 2.0.0](https://semver.org) line. A
line moves only when its own contract changes. Nobody picks version numbers:
- every change is recorded once, when it lands, under **Unreleased** in its changelog, in one of a fixed set
  of classes;
- `tools/release.py` computes the single bump a release calls for.

PATCH is the default. MINOR and MAJOR happen only when a contract really grows or breaks, and many changes
share one bump.

## Motivation

Bumping per change, or by feel, makes version numbers noisy. Every accepted SREP would become a MINOR, and
engines and packages would chase numbers that don't tell them anything. A version should answer one
question: "do I need to change anything?"
- PATCH: no.
- MINOR: only to use something new.
- MAJOR: yes.

## Specification

### Version lines

| Line | Where the version lives | Tag | Changelog | Contract |
|---|---|---|---|---|
| sr-core distribution | `sr_core.__version__` (the only copy; `pyproject.toml` reads it; `scenerender-vpkg` and `sr-schemadoc` report it) | `vX.Y.Z` | `CHANGELOG.md` | command names, options, exit codes and output files; the URL layout of the generated reference (`index.html`, `elements.html`, `type/<type>.html#a-<attribute>`, …) |
| scene schema | `xs:schema/@version` in `schema/scene-render.xsd` | `schema-X.Y.Z` | `schema/CHANGELOG.md` | which documents are valid and how they render |
| package format | `formatVersion` in `vpkg.json`; `FORMAT_VERSION` in the tool | none (it changes only through an SREP, recorded in `CHANGELOG.md`) | SREP 1 | the meaning of `vpkg.json` and the zip layout |

The Python modules are internal. They may change in any release, and they are not part of the
distribution's contract.

### Classes and bumps

| Class under Unreleased | Bump |
|---|---|
| `Breaking`, `Removed` | MAJOR |
| `Added`, `Deprecated` | MINOR |
| any other (`Changed`, `Fixed`, `Security`, `Docs`, …) | PATCH |

A release takes the largest bump among the classes that have entries. Unreleased entries then move under
the new version's heading. An empty Unreleased section releases nothing.

What counts as Breaking:
- **Schema:** a document that was valid becomes invalid, or renders differently.
- **Distribution:** a command, option, exit code, output file or reference URL that someone could script
  against changes meaning or disappears.

Anything that only adds is Added. Anything with no observable change to the contract is PATCH.

### Documents and formats declare MAJOR.MINOR

- A scene declares `version="MAJOR.MINOR"`. A schema MINOR release adds its MAJOR.MINOR to `scene/@version`,
  and `tools/release.py` refuses to cut one that doesn't.
- `formatVersion` is MAJOR.MINOR.
  - A reader of 1.N reads 1.0 to 1.N strictly, and reads a later 1.M by ignoring and reporting what it doesn't
    know. It refuses other majors.
  - A writer never writes a version newer than its own.
  - So a format MINOR may only add what an older reader can safely skip.

### Tooling

- `python3 tools/release.py check` fails when:
  - a version disagrees with the newest release in its changelog;
  - the schema's MAJOR.MINOR isn't accepted by `scene/@version`;
  - `schema/SHA256SUMS` or `docs/schema/` is stale;
  - the package-format schema file doesn't match `FORMAT_VERSION`.
- `python3 tools/release.py next tools|schema` prints the version the Unreleased entries call for.
- `python3 tools/release.py release tools|schema [--date D]` does the following:
  1. moves the entries under a dated heading;
  2. writes the version;
  3. refreshes the hashes and the reference;
  4. prints the tag to create. It never commits or tags.

## Rationale

Classifying at the moment of change is cheap and accurate. The author knows then whether the change breaks
anyone. Computing the bump at release time makes the number a summary of the release rather than a count of
changes.

Keeping documents on MAJOR.MINOR means the frequent PATCH releases never ask anyone to edit a scene.

## Rejected alternatives

- **One version for everything.** A documentation fix in the schema would bump the package tools, and a new
  CLI option would bump the schema. None of the three numbers would mean anything.
- **Version per SREP.** Every accepted SREP would be a MINOR, even when several land together.
- **Commit-message conventions.** They classify commits, not contract changes: one commit can carry several
  classes, and one contract change can span several commits.

## Backwards compatibility

- **Distribution:** starts at 1.0.0.
- **Schema:** starts at 1.1.1. The 1.1.0 baseline plus SREPs 2 and 3, both documentation-only, make one
  PATCH.
- **Package format:** stays 1.0. Its reader now accepts later 1.x manifests leniently. Before, it rejected
  their unknown keys.
