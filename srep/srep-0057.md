# SREP 57 — Accept the marker ids a `beatGrid` generates (`beat.N`, `bar.N`)

## Abstract

The annotation of `beatGridType` promises that "keys can snap with @marker to generated ids beat.N and bar.N". The Rust reference
resolves them (`marker_time`), but every attribute that names a marker is an `xs:IDREF`, which can only equal an `xs:ID`
that some element carries, and Schematron rule R21 requires an explicit `<marker>`. A document that uses `startMarker="beat.3"`
therefore fails validation. This SREP types the five marker references as `xs:NCName`, makes R21 accept a generated id when the
scene has a `beatGrid`, adds the warning W04 for a `poster` or `thumbnail` marker that names no marker, and adds the warning W03 for an explicit marker that
would collide with a generated id (the explicit marker wins, as the evaluator already does).

## Motivation

The G2 lab repro `repros/beatgrid-generated-ids` (four scenes, `scene-render validate`): `startMarker="beat.3"`,
`startMarker="bar.2"` and `<key marker="beat.4"/>` each exit 1 with R21 ("marker references must name markers") and S10 ("no
element has that id"); the control, an explicit `<marker id="m3" time="1.25"/>` beside the grid, exits 0. Under SREP 0 ("a validator
that accepts what rendering rejects is a defect of the Schematron") the converse holds too: a validator that rejects what the
annotation promises and the engine renders is a defect.

## Specification

### Syntax

The five attributes that name a marker change their type from `xs:IDREF` to `xs:NCName`:

```xml
<!-- keyType -->        <xs:attribute name="marker"      type="xs:NCName"/>
<!-- the timing group (line 1389-1390 of the 1.1.4 schema) -->
                         <xs:attribute name="startMarker" type="xs:NCName"/>
                         <xs:attribute name="endMarker"   type="xs:NCName"/>
<!-- audioTrackType -->  <xs:attribute name="startMarker" type="xs:NCName"/>
<!-- stillType (the poster and thumbnail elements of an output) -->
                         <xs:attribute name="marker"      type="xs:NCName"/>
```

`beat.3` and `bar.2` are NCNames (a `.` is a name character). The reference checking that the IDREF type gave for explicit
markers moves to R21, which still applies as an error to `key/@marker`, `startMarker` and `endMarker` only. The `marker` of `poster` and `thumbnail` (the elements of `stillType`) was an `xs:IDREF` that any element id satisfied, so a document could point it at a non-marker element; making that an error would reject a valid document (MAJOR), so it gets the warning W04 instead.

With `G(x)` standing for the test "x is a generated id":

```
(substring-before(x,'.')='beat' or substring-before(x,'.')='bar')
and string-length(substring-after(x,'.')) > 0 and string-length(substring-after(x,'.')) < 20
and translate(substring-after(x,'.'),'0123456789','')=''
```

W04 is not a Schematron rule (the document is valid and renders; like W01 and W02 it is a warning of the validator): `poster/@marker` and
`thumbnail/@marker` that name neither an explicit marker nor, with a `beatGrid`, a generated id are reported as warnings.

```xml
<sch:pattern id="p37">
  <sch:rule context="*[@startMarker] | *[@endMarker] | key[@marker]">
    <sch:assert id="R21" test="
        (not(@startMarker) or /scene/markers/marker[@id=current()/@startMarker]
           or (/scene/markers/beatGrid and G(@startMarker)))
    and (not(@endMarker)   or /scene/markers/marker[@id=current()/@endMarker]
           or (/scene/markers/beatGrid and G(@endMarker)))
    and (not(@marker)      or /scene/markers/marker[@id=current()/@marker]
           or (/scene/markers/beatGrid and G(@marker)))">marker references must name a marker, or a beat.N or bar.N id of the scene's beatGrid.</sch:assert>
  </sch:rule>
</sch:pattern>

```

(`G(x)` is written out in the file; XPath 1.0 has no user functions. The check of one to nineteen digits is the range of the
engine's unsigned 64-bit parse, less one digit.)

### Semantics

**1. Generated ids.** A scene with a `beatGrid` of `bpm`, `offset` and `beatsPerBar` defines, for every non-negative integer `N` of
one to nineteen decimal digits (leading zeros allowed): `beat.N` at the time `offset + N · 60/bpm` and `bar.N` at
`offset + N · beatsPerBar · 60/bpm`, in composition seconds. `beat.0` and `bar.0` are the offset. There is no upper bound on `N`
in the grid: a generated time may lie beyond the composition's duration. (This is what the Rust reference computes; the
annotation did not give the numbering.)

**2. Explicit markers.** A scene with a `beatGrid` that declares an explicit `<marker>` whose id is a generated id is valid, and
the explicit marker wins (the evaluator looks explicit markers up first). A validator SHOULD warn (W03, not a Schematron rule: the
document is valid and renders), because the grid's own time is then unreachable under that name. A scene without a
`beatGrid` may name a marker `beat.3` as any other, with no warning.

**3. No grid, no generated ids.** `startMarker="beat.3"` in a scene with no `beatGrid` and no marker of that id fails R21.

**4. One grid.** A scene with several `beatGrid` elements resolves generated ids against the first, as the engine does; the number
of `beatGrid` elements is not constrained by this SREP (Open issues).

### Defaults and the neutral case

A scene that references only explicit markers behaves as before: R21 holds exactly when it held (the explicit marker exists),
and the `marker` of `poster` and `thumbnail` is now checked, as the other attributes always were.

## Rationale

- **NCName, not a custom pattern**: the schema already uses `xs:IDREF` only to get a reference; a generated id is not an element
  id, and R21 now does the reference check, in one place, with the grid's rule.
- **W04 for poster and thumbnail**: moving the type away from IDREF drops the existence check these two had (a dangling id is no longer an XSD error, which loosens an error to a warning), and a new error would reject documents that point them at a non-marker element,
  (IDREF existence) without a replacement.
- **A warning for the collision**, not an error: such a document is valid and renders today (the explicit marker wins), and
  SREP 0 makes turning a valid rendering document into an invalid one a MAJOR change. The warning says which time `beat.3` means.
- **No range bound**: the evaluator has none; a bound would be a rule that rejects what renders.

## Rejected alternatives

- **Declaring the generated ids as xs:ID elements by a transform**: the document would change under the author.
- **An `xs:pattern` union of NCName and the generated forms**: it cannot know whether the scene has a `beatGrid`.
- **An error for the collision **: clearer, but MAJOR; recorded under Open issues.

## Backwards compatibility

Class: Standards, MINOR: looser in the type and in the rule that accepts the ids (more documents are valid), plus a warning. A
document that has a `beatGrid` and an explicit `<marker id="beat.N">` or `"bar.N"` stays valid and renders as before (the
explicit marker wins); it gains W03. A document that points the `marker` of a `poster` or `thumbnail` at a non-marker element, or at no element, gains W04 and renders
as before; a dangling id there, which the IDREF type rejected, is now valid with the warning (a loosening).

## Open issues

- Promote W03 to an error in the next MAJOR version (an explicit marker may then not take a generated id), and W04 likewise
  (`poster/@marker` and `thumbnail/@marker` must then name a marker, as the other references do).
- Several `beatGrid` elements: the engine uses the first; whether more than one should be an error.
- A grid that names an audio `source`: the Rust reference holds detected beat times for it (`sr-eval/src/program.rs`, "Detected beat times in seconds, when a beat grid names an audio source"); how they relate to the generated ids is not specified here.
- A generated time beyond the composition's duration: legal here; a warning for a `startMarker` that starts after the end would be a
  separate rule.
