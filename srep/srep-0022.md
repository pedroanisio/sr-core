# SREP 22 — Publish engine capability manifests

## Abstract

Each engine publishes a **capability manifest**: one JSON file listing every construct of the scene format
(element, attribute or enumeration value) that it does not draw exactly, with its status: `approximate`,
`reported` or `unsupported`. Tools read it to choose an engine for a scene and to tell the author what will
be missing before a render. When rendering, an engine reports each such construct a document uses as
`SUP-APPROX` or `SUP-REPORTED` in the render report of [SREP 18](srep-0018.md). The format is maintained in
sr-core, like the package format of [SREP 1](srep-0001.md).

## Motivation

- **What each engine leaves out is written four ways.**
  - The C engine keeps its own table of 2,105 constructs (elements, attributes, enumeration values):
    1,718 missing, 131 partial, 256 supported.
  - DEFINITIONS.md lists "Reported" items in prose, per definition.
  - The other engines keep no list.
- **Nobody can ask before rendering.** Neither an author choosing an engine nor `scenerender-vpkg run` can
  ask whether an engine draws a given scene.
- **Precedent.** The FrameForge engine reports each unsupported construct explicitly (for example
  `gradient_conic_unsupported`) instead of substituting silently.

## Specification

### Form

An engine publishes its manifest at a stable place in each release: `capabilities.json` at the root of its
repository and in its distribution.

```json
{
  "format": "scene-render-capabilities/1",
  "engine": {"name": "c-scene-render", "version": "1.4.0"},
  "schema": "1.1.3",
  "entries": [
    {"construct": "particleEmitter", "status": "unsupported"},
    {"construct": "layer/@frameBlend=optical-flow", "status": "reported", "definition": "D20"},
    {"construct": "effect/@type=glow", "status": "approximate", "note": "bloom radius capped at 64 px"}
  ]
}
```

### Semantics

1. **`construct`** is one of:
   - an element name;
   - `element/@attribute`;
   - `element/@attribute=value`, for an enumeration value.
2. **`status`:**
   - `exact`: passes the kit's cases for it;
   - `approximate`: drawn, measurably different;
   - `reported`: recognised, not drawn, reported as `SUP-REPORTED`;
   - `unsupported`: not recognised.
3. **Coverage.** A construct the manifest does not list is claimed `exact`. The manifest MUST list every
   other one, for the `schema` version it names.
4. **Reporting.** When rendering with a report (SREP 18), an engine reports each `approximate` or
   `reported` construct the document uses, once, as `SUP-APPROX` or `SUP-REPORTED` (warning), with the
   construct in `message`.

### Defaults and the neutral case

No syntax in documents; no picture changes.

## Rationale

- **The list exists and is large.** The C engine's table shows it; one format lets every tool read every
  engine's.
- **Omission means exact.** Engines list their gaps, not their features, so the manifest stays short for a
  complete engine.

## Rejected alternatives

- **A capability flag per element in the XSD (`xs:appinfo`).** Capabilities belong to engines and change with
  their releases; the schema changes only through SREPs.
- **Inferring support from the kit alone.** The kit covers what SREPs define cases for, not every attribute.

## Backwards compatibility

A new format beside the scene format. No document changes validity or picture.

  version records them in `note`.
