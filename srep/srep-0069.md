# SREP 69 — Add stepping programs: `<program mode="step">`

## Abstract

A `program` (SREP 66) with `mode="step"` keeps state and advances it per frame. Its WebAssembly module exports
three functions:

- `init`, called once;
- `step`, called `stepsPerFrame` times per frame, after `prewarm` steps before the first frame (SREP 68);
- `frame`, which returns a width × height RGBA picture that the node draws.

The module's state (its memory, its globals and its random generator) is bit-exact under the determinism rules of
SREP 66. Its checkpoints are therefore exact too. Agent systems that a pixel shader cannot express, such as
Langton's ant, diffusion-limited aggregation and dendritic frost, become documents.

## Motivation

**The owner's 72-cell atlas test (2026-10-09, not published).** The owner lists "support for sequential agents,
such as Langton's ant, DLA and dendritic frost" among the iteration gaps. The plan does not count these cells
separately; they sit with the per-node iteration of SREP 68. These algorithms move one agent, or a few, through a
grid, one step at a time. Each step reads and writes cells that the previous step chose. A fragment shader computes
every pixel independently, so it cannot express them. A compute shader could only do so serially, with float state.

**Today** (`rs-scene-render` commit `c09b58a`): the agent systems in the format are fixed native nodes, namely
`flock` (Reynolds boids, `crates/sr-sim/src/flock.rs`), `slime` and `erosion`. Their algorithms cannot be changed
from a document. There is no WebAssembly runtime (SREP 66).

## Specification

### Syntax

```xml

</xs:attribute>

```

A program in `parameters` (`programDataType`) has no `mode`. A data program is always a build program.

### Semantics

**1. The module interface in step mode.** The module MUST export:

| Export | Type | Role |
|---|---|---|
| `memory` | memory | as SREP 66 |
| `init` | `[] → []` | called once, after instantiation, to set the zero state |
| `step` | `[i64] → []` | advances the state by one step; the argument is the index of the step, counted from 0 including prewarm steps |
| `frame` | `[] → [i64]` | returns `(ptr << 32) | len` of the picture (2) |

It does not need to export `generate`. A missing or mistyped export is error **PRG11**. The imports allowed, and
every determinism rule, are those of SREP 66. The random generator (SREP 66, Semantics 4) is seeded once, before
`init`, and continues across `init`, the steps and `frame`. It is part of the state.

**2. The picture.** `frame` returns `len = width · height · 4` bytes: RGBA, 8 bits per channel, rows from the top,
straight (not premultiplied) alpha. The colour values are display-encoded code values, read as colour literals
are (CONVENTIONS 1.4). Any other length is error **PRG14**. The node draws the picture as a width × height image
with its top-left corner at the node's local origin, one pixel per unit. The node's transform, timing, opacity,
masks, matte, effects and `blend` apply as for a `layer`.

**3. Steps.** The step schedule is SREP 68, Semantics 1, with the program in place of the (effect, node) pair. Let
f₀ be the program's first active frame, k = `stepsPerFrame` and p = `prewarm`.

- **Before f₀:** `init()`, then `step(i)` for i = 0 … p − 1.
- **At each active frame f:** `step(i)` k more times, with consecutive indices, then `frame()`.

After frame f the module has run p + (f − f₀ + 1)·k steps. Inside an `iterate` (SREP 67), the program restarts
from `init()` at each frame and runs the `iterate`'s steps. A step program has no image input, no time input and
no access to other nodes. Its state is therefore a function only of its module, parameters, seeds, k, p and the
number of active frames.

**4. Fuel.** `fuel` (SREP 66, Determinism 4) is the budget of each call (`init`, each `step`, each `frame`),
counted from zero at the start of each call. Exceeding it is error **PRG12**.

**5. Render-order independence and checkpoints.** SREP 68, Semantics 2 and 3 apply. The state of a stepping
program is its linear memory, its mutable globals, its tables and the random generator's position. The determinism
rules make this state bit-exact on every conforming engine. A checkpoint is a copy of it.

### Errors

| Code | When | Stage |
|---|---|---|
| PRG3 | `mode="step"` without `width` and `height` | validation |
| STP1 | `stepsPerFrame` or `prewarm` on a program in build mode | validation |
| PRG11 | a missing or mistyped `init`, `step`, `frame` or `memory` export (and the other causes of SREP 66) | build |
| PRG12 | a call exceeds `fuel` | render |
| PRG13 | a trap in `init`, `step` or `frame` | render |
| PRG14 | `frame` returns a length other than width · height · 4 | render |

### Defaults and the neutral case

A program without `mode` is a build program (SREP 66), so nothing else changes.

## Rationale

- **The picture is the only output.** It covers the three cases the owner named, and it keeps the per-frame cost
  bounded by the picture's size. Emitting nodes per frame is left open (Open issues).
- **An exact state.** WebAssembly integer and float arithmetic under SREP 66's rules is reproducible. The checkpoint
  of a stepping program is therefore exact on every host, unlike the float GPU state of SREP 68's shader effects.
- **No time input.** A step program advances by steps, not by seconds. Its picture at frame f depends only on
  how many steps it has run, so changing `fps` changes only how fast it plays.

## Rejected alternatives

- **A separate element** (`<agent>`, `<automaton>`): it would repeat SREP 66's module rules. The mode is the only
  difference.
- **Native nodes for Langton's ant, DLA and frost**: three fixed algorithms where one mechanism covers them and
  others.
- **Passing the step index through an import**: the plan restricts imports to the RNG and parameter reads. The
  index is an argument instead.

## Backwards compatibility

The change is MINOR. It adds attributes to an element that SREP 66 introduces under the version gate V12.

## Conformance

The cases are in `conformance/srep_cases/srep-0069.json`. They are written, with the modules
`srep_cases/assets/srep69-*.wasm`, by `conformance/tools/srep69_cases.py`.

- **Modules.** The counter module counts its steps. The rng module XORs the next generator value into a global at
  each step.
- **Pictures.** Each module draws a 100 × 100 picture, red or blue according to a test on its state.
- **Checked in V8.** Run under Node 24.18.0 (V8) with a stand-in host, the counter module drew red after 1 step
  with target 1, blue after 1 step with target 2, and red after 5 steps with target 5. The rng module drew red after
  5 steps with seed 1, as the generator of SREP 66 predicts (2026-10-09).

All cases are pending.

| Case | Checks | Tolerance |
|---|---|---|
| `srep-0069-step-frame-0`, `-short` | 1 step at frame 0 (3) | 2 px |
| `srep-0069-step-per-frame`, `-short` | `stepsPerFrame="5"` (3) | 2 px |
| `srep-0069-step-prewarm` | `prewarm="4"` gives 5 steps at frame 0 (3) | 2 px |

| `srep-0069-step-needs-size`, `-build-mode-no-steps` | PRG3, STP1 | exact |

## Open issues

- Emitting nodes per frame (for example, agents drawn as shapes) instead of a picture.
- A picture larger than the node: should `width` × `height` allow a scale, so that a 200 × 200 grid can fill a
  1000 px cell? Today the node's `scaleX` and `scaleY` do this, and the layer resampling filters of SREP 32 apply.
- An image input, such as reading another node's picture, would let a step program react to the scene. It is left
  out to keep the state independent of other nodes.
