# SREP 85 — Decimal and double attributes are tested by value (amends SREP 67)

## Abstract

Eighteen Schematron rules of sr-core 1.5.0 (C13, C14, C15, C37, C38, C44, C52, C53, C54, C56, PYRO1, PYRO2, PYRO4,
VOL4, P3D3, P3D10, OCN3, OCN5), three of the drafts SREP 78 and SREP 80 (PYRO11, PYC6, FRX11) and two of the draft
SREP 67 (ITR1, SRT1) read an `xs:double` attribute (or a type derived from it, such as `positiveDecimal`), an item of
a list of them, or an `xs:positiveInteger`, through XPath 1.0's `number()`, `sum()` or a bare comparison. XPath 1.0
reads no leading `+`, which the XSD accepts, so `"+1"` and `"+0.5"` are NaN to these rules: a rule refuses a valid
document (it misfires) or accepts one it exists to refuse (it is bypassed). This SREP reads each of these attributes
with the sign-stripping form that SREP 84 uses for integers, and VOL6 before it:
`number(substring(normalize-space(@a),1+number(starts-with(normalize-space(@a),'+'))))`. Exponent forms (`1e0`),
which a strict XPath 1.0 `number()` does not read either, are left to the native validator, which this SREP makes
normative for them. The XSD does not change, and no kit case outside this SREP changes verdict.

## Motivation

- **The lexical forms are values of the XSD.** `xs:decimal` is "a finite-length sequence of decimal digits ...
  separated by a period as a decimal indicator. An optional leading sign is allowed" (XML Schema 1.0 Part 2, 3.2.3.1),
  and `xs:double` is a decimal mantissa "followed, optionally, by the character 'E' or 'e', followed by an integer
  exponent", or one of `INF`, `-INF`, `NaN` (3.2.5.1). Both collapse whitespace (4.3.6). Every numeric type of the
  schema that these rules read (`positiveDecimal`, `unitDecimal`, `nonNegativeDecimal`, `durationType`,
  `numberListType` and the inline restrictions) is a restriction of `xs:double` or a list of it; the four `xs:decimal`
  attributes of the schema (the draft SREP 75's fractal centre and Julia point) are read by no rule. A document that
  writes `speed="+1"`, `minSize="+0.5"` or `scaleX="1e0"` passes the XSD with the values 1, 0.5 and 1.
- **The reference reads the value.** The reference engine's model reads an `xs:double` with an optional sign and an
  exponent (`rs-scene-render`, `crates/sr-model/src/parse.rs`, `ParseValue for f64`, through
  `crates/sr-model/src/xsd/mod.rs`, `parse_xsd_double`; at `prep/srep-84-boolean-forms` ea8750bd). It renders a
  layer with `speed="+1"` at speed 1, while C15 refuses its `timeRemap`.
- **XPath 1.0 reads no `+` and no exponent.** `number()` converts "optional whitespace followed by an optional minus
  sign followed by a Number followed by whitespace"; "any other string is converted to NaN" (XPath 1.0, 4.4), and
  `Number ::= Digits ('.' Digits?)? | '.' Digits` (3.7). `sum()` converts each node the same way (4.4). So `"+1"` and
  `"1e0"` are NaN, and every comparison with NaN is false (3.4, IEEE 754). libxml2, which the kit's tests use, extends
  `number()` with an exponent and still reads no `+`: under lxml (libxml2 2.9.14), `number('1e0')` is 1 and
  `number('+1')` is NaN (checked for this SREP). The `+` is what breaks every XPath 1.0 processor; the exponent breaks a
  strict one.
- **SREP 84 left them open.** SREP 84 read the integer attributes by value and listed these as an open issue
  ("Numbers of type `xs:double`"), and its ITR1 (draft SREP 67) as another. Several rules already read their doubles
  this way: VOL6, MSQ2 and the drafts' lets for the crater, the black hole and the voxel scales take the `+` off with
  this form, and CRT4 and FRX4 test finiteness with it; PYRO8, P3D6, OCN7 and the draft SREP 79's OCN14 take it off with
  `translate(@a,'+','')`. The rules below are the rest.

## Specification

### Syntax

The XSD does not change. The Schematron change is two diffs and one amendment of the draft SREP 67. The first diff
is against `schema/scene-render.sch` of schema 1.5.0 with SREP 84 applied, whose line numbers are those of 1.5.0
(SREP 84 changes lines one for one). The second changes the rules of the drafts SREP 78 and SREP 80, against the files
with the drafts SREPs 76 to 81 and their amendments, SREP 83 and SREP 84, after the first (`conformance/tools/
engine_gap.py`, `proposed_schema`; its line numbers). Neither has context lines: each removed line occurs once, so both
apply by content to those files.

Each added line is the removed line with two substitutions and nothing else, where `P` is an attribute path
(`@a`, `../@a`, `preceding-sibling::stop[1]/@a`, `whitewater/@a`, `/scene/project/@duration`) or a list item (`.`,
`preceding-sibling::*[1]`, `following-sibling::*[n]`):

- `number(P)`, and a bare `P` that a comparison converts to a number, become
  `number(substring(normalize-space(P),1+number(starts-with(normalize-space(P),'+'))))`;
- `sum(P)` becomes `number(concat(substring(normalize-space(P),1+number(starts-with(normalize-space(P),'+'))),substring('0',1,number(not(P)))))`.

### Semantics

1. **Decimals and doubles.** A rule that reads an `xs:double` or `xs:decimal` attribute `a` as a number (or a type
   derived from one, or an item of a list of one) MUST read its value, whatever its sign or the whitespace around it.
   In XPath 1.0 that is `number(substring(normalize-space(@a),1+number(starts-with(normalize-space(@a),'+'))))`, the
   form of SREP 84 for integers: `normalize-space` strips the whitespace that the XSD collapses (XPath 1.0, 4.2; XML
   Schema 1.0 Part 2, 4.3.6), and a leading `+`, which `number()` refuses, is removed. Where the rule summed the
   attribute to read an absent one as 0, the form is
   `number(concat(substring(normalize-space(@a),1+number(starts-with(normalize-space(@a),'+'))),substring('0',1,number(not(@a)))))`,
   the form of the crater's lets: `'0'` is appended only when the attribute is absent.
2. **Nothing else changes.** For a string `s` that does not start with `+` once whitespace is collapsed,
   `starts-with` is false, `substring(normalize-space(s),1)` is `normalize-space(s)`, and `number()` of that is
   `number(s)`: `number()` itself ignores leading and trailing whitespace (XPath 1.0, 4.4), and a string with inner
   whitespace is NaN under both. An absent attribute gives `number('')`, NaN, as `number()` of an empty node-set does,
   and, in the second form, `number('0')`, 0, as `sum()` of an empty node-set does. So each rule reads every value it
   read before as it read it, and in addition the values written with `+`. The rule ids, contexts and messages, and
   the parts of the tests that read other things, are unchanged.
3. **Integers.** ITR1's attributes are `xs:positiveInteger`; the form is the integer form of SREP 84, which reads them
   completely (an integer has no exponent). This SREP applies it to ITR1, SREP 84's second open issue.
4. **Exponents and the special values: the native validator is normative.** `xs:double` also has exponent forms
   (`1e0`, `5E-1`). XPath 1.0's `number()` reads none (3.7, 4.4), and no XPath 1.0 expression of reasonable size
   converts them; libxml2's `number()` reads them as an extension. For a document that writes an attribute read by a
   rule of this SREP (or of SREP 84) in an exponent form, the verdict of the rule is the one it has with the value of
   the attribute, which a native validator that mirrors the Schematron in its own code MUST compute; that verdict is
   normative, and a Schematron processor that reads exponents as NaN can disagree with it. The reference's native
   validator reads exponents (`xpath_number`, `crates/sr-model/src/rules.rs`), so for these documents it gives the
   verdict that lxml does. The special values `INF`, `-INF` and `NaN` are outside this SREP: XPath 1.0, libxml2 and
   the reference's native validator all read them as NaN, as before (Open issues).
5. **Native validators.** A validator that mirrors the Schematron in its own code MUST read the attributes of these
   rules by value, with the sign and, by 4, the exponent. The reference does (Engine impact).
6. **Types.** The types of the attributes do not change. A pattern facet that refused `+` or exponents would make
   documents valid today invalid (Rejected alternatives).

## Rationale

- **The value is what the XSD defines and what renders.** A rule that guards a rendering choice has to fire on the
  documents that make that choice, and only on them. SREP 84 made the rules read booleans and integers by value; the
  doubles are the same defect in more rules.
- **One form.** The form is SREP 84's for integers and VOL6's before it, and the crater's for defaulted reads, so the
  rules use one reading of a number and a reviewer can check a line by writing it back (Conformance). The native
  mirror needs one function for it (the reference's `xs_number`).
- **XPath 1.0.** The Schematron's `queryBinding` is `xslt` (XSLT 1.0, XPath 1.0): there is no `xs:double()`
  constructor, no `if`, and no way to map a conversion over a node-set, so the conversion is spelled out at each read.
- **Exponents.** Converting an exponent in XPath 1.0 would take a power of ten from a string, which needs recursion
  (a named template) or a lookup table of every exponent; neither fits in an assertion. The engine that renders the
  document reads the exponent, so its validator is the one that can give the verdict the value deserves.

## Rejected alternatives

- **Restrict the XSD to unsigned, exponent-free forms.** A pattern facet on these types would make every document that
  writes `+1` or `1e0`, valid today, invalid: Breaking under SREP 4. It would also differ from every other number of
  the schema. The owner's decision of 2026-10-10 keeps the types.
- **`translate(@a,'+','')`.** It reads the same values on the lexical space of `xs:double` (see the inventory), and
  four rules use it. It was not taken for the rules of this SREP because SREP 84 took the other form for integers, and
  one form for both keeps the rules alike; the four rules that use it are correct and left as they are.
- **Leave the misfires and bypasses.** They refuse valid documents that a renderer renders, and accept documents
  whose rendering the rule exists to prevent (gradient stops out of order, a pyro source with a zero scale, a
  whitewater window that ends before it starts, a wave shorter than two cells).

## Open issues

- **`INF`, `-INF` and `NaN`.** `xs:double` has them, and the types without a bound (`xs:double` itself: C15's `speed`,
  C44's and C52's `start` and `end`, the bounds of VOL4, the finite attributes of OCN3, PYC6's `x`, `y`, `z`) admit
  them. XPath 1.0 reads them as NaN, and so do this SREP's form and the reference's native validator; the model reads
  `INF` as infinity (`parse_xsd_double`). A rule meets NaN: OCN3, VOL4, CRT4 and FRX4 refuse it as not finite, which is
  their meaning; the others refuse or accept by the NaN comparison, as before this SREP. Whether a rule should read
  `INF` as infinity is a decision of its own; this SREP does not change it.
- **Exponents in a strict processor.** Semantics 4 makes the native validator normative for them; a Schematron-only
  validator with a strict XPath 1.0 `number()` gives a different verdict for a document that writes an exponent, and
  cannot be fixed within XPath 1.0.
- **Messages.** The messages describe the values and are left as they are.
