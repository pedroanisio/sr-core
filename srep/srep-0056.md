# SREP 56 — Add stroke-order text from single-line fonts

## Abstract

Text in the schema is filled glyph outlines; a written-on, stroke-by-stroke handwriting is not available. A new asset
kind, `strokeFont`, names a single-line font file (a vector font whose glyphs are lists of pen strokes, such as the Hershey
fonts, in the `jhf` format), and a new shape kind, `shape="stroke-text"`, lays a string out in it as one path of open
strokes, in the order the font gives them. The path is an ordinary shape outline: it takes `stroke`, `strokeWidth`, caps,
`trimStart`/`trimEnd` in `sequential` mode (the text is written on, left to right, stroke by stroke), markers, dashes
and the shape modifiers (`wiggle-path`). A document that uses neither the asset nor the shape kind renders as before.

## Motivation

The whiteboard style's feature gap F2: "no stroke-order text: a written left-to-right reveal of a font is not available",
so handwriting (W9) stays APPROXIMATED, built by hand from "own single-line capitals as paths, each letter drawn with
`trimEnd`", or by a mask-rect wipe of finished glyphs (whiteboard style, ENGINE-DEFECTS.md). With the Rust reference the text
presets reveal a line through its own box (`mask-reveal`) or by character (`typewriter`), neither of which follows the
strokes of a letter.

## Specification

### Syntax

```xml

<xs:element name="strokeFont" type="strokeFontAssetType"/>

<xs:complexType name="strokeFontAssetType">
  <xs:annotation><xs:documentation>A single-line font: glyphs as pen strokes. format="jhf" is the Hershey font file
  format; the n-th glyph of the file (counting from 0) is the character U+0020 + n. Version 1.2.</xs:documentation></xs:annotation>
  <xs:attribute name="id" type="xs:ID" use="required"/>
  <xs:attribute name="src" type="xs:anyURI" use="required"/>
  <xs:attribute name="format" default="jhf">
    <xs:simpleType><xs:restriction base="xs:string"><xs:enumeration value="jhf"/></xs:restriction></xs:simpleType>
  </xs:attribute>
  <xs:attributeGroup ref="assetProvenance"/>
</xs:complexType>

<!-- shapeType: the enumeration of @shape gains stroke-text, and it gains -->
<xs:attribute name="text" type="xs:string"/>
<xs:attribute name="strokeFont" type="xs:IDREF"/>
<xs:attribute name="fontSize" type="positiveDecimal" default="48"/>
```

```xml
<!-- the version gate, V5: documents before version="1.2" cannot use 1.2 elements -->
<sch:assert id="V5" test="not(assets/tiles|…|assets/strokeFont|.//shape[@shape='stroke-text'])">

<sch:rule context="shape[@shape='stroke-text']">
  <sch:assert id="PEN1" test="@text and @strokeFont">shape="stroke-text" needs @text and @strokeFont.</sch:assert>
  <sch:assert id="PEN2" test="not(@strokeFont) or /scene/assets/strokeFont[@id=current()/@strokeFont]">shape/@strokeFont must name a strokeFont asset.</sch:assert>
</sch:rule>
```

`@text`, `@strokeFont` and `@fontSize` apply to `shape="stroke-text"` only; on other shapes they have no effect and a validator
SHOULD report them as inert (SREP 18). The shape's `width` and `height` remain required, and are the box the node's
transform, alignment and paints use; the strokes are not clipped to it.

### Semantics

**1. The `jhf` format.** A file is a sequence of records. A record is the glyph number (5 characters), the number `n`
of coordinate pairs including the margin pair (3 characters), then `2n` characters: first the left and right margins of the
glyph, then `n − 1` coordinate pairs. Every coordinate character is the coordinate plus the code of `R` (82), so the value
is the character code minus 82. The pair ` R` (a space and `R`) lifts the pen and moves it. The data of a record may be
wrapped over several lines: a reader takes exactly `2n` characters after the count, ignoring line ends. In the font's
coordinate system the origin is the glyph's centre, x grows to the right and y downwards. Glyph numbers are not read:
the glyphs are the records in file order.

**2. Glyph geometry.** A glyph has left margin `l`, right margin `r`, and strokes: maximal runs of points between pen lifts
(a run of one point draws nothing). Its advance is `r − l`.

**3. Scale and origin.** The `jhf` fonts of the Hershey set put the baseline at y = 9, the top of the capitals at y = −12 (a cap
height of 21 units) and the descenders to about y = 16. The scale is `s = fontSize / 21`: `fontSize` is the cap height in
node units. A point `(x, y)` of a glyph whose pen is at `cx` on a line whose baseline is at `by` is drawn at
`(cx + (x − l)·s, by + (y − 9)·s)`; the first baseline is at `by = fontSize` (the tops of the capitals touch the top of the
box) and the pen starts at `cx = 0`.

**4. Layout.** The characters of `@text` are laid out left to right: the pen advances by the glyph's advance times `s` after each
character. A line feed (`&#10;`) starts a new line: the pen returns to 0 and the baseline moves down by `fontSize · 32 / 21`
(the 32 units of the font's em). A character that the font has no glyph for (beyond its record count, or a control character
other than the line feed) is skipped, advances nothing, and MUST be reported once for the shape. A space has the advance of
its glyph and no strokes.

**5. The outline.** The shape's outline is the path of every stroke of every character in text order, each stroke a subpath
`M p₀ L p₁ L … L pₖ` that is not closed. It is an ordinary shape outline in every respect except one: `fill` is not used (open
strokes have no inside), so the glyphs are drawn only by `stroke`. Trimming (`trimStart`, `trimEnd`, `trimOffset`) in
`sequential` mode walks the strokes in this order across the whole text, so `trimEnd` from 0 to 1 writes the text on; in the
default `simultaneous` mode every stroke is trimmed on its own.

### Defaults and the neutral case

A document without a `strokeFont` asset or a `stroke-text` shape is unaffected. A `stroke-text` shape draws nothing until it
has a visible `stroke`.

## Rationale

- **An asset kind for the font**, so that the file is hashed, verified and cached as every other input (SREP 28);
  the engine bundles no font data. The Hershey fonts are available under a licence that allows any use if their
  acknowledgements travel with the font data ("The Hershey Fonts were originally created by Dr. A. V. Hershey while working at
  the U. S. National Bureau of Standards. The format of the Font data in this distribution was originally created by James Hurt,
  Cognition, Inc."; the data may be converted into any format except the NTIS format; read in the distribution notice
  at emergent.unpythonic.net/software/hershey, 2026-10-05); a document that uses one supplies the file and the acknowledgements.
- **A shape kind**, not a text layer feature: the stroke machinery (draw-on by trimming, caps, dashes, markers, wiggle)
  already belongs to shapes, and a stroke font has nothing a text layer's shaping, wrapping or fallback could add.
- **Sequential trim for the order**: the trim modes already say whether the strokes are one outline or many; no new notion.
- **Cap-height scale**: the Hershey data fix the cap height at 21 units; a size in cap heights is the one an author can see.

## Rejected alternatives

- **Deriving strokes from outline fonts** (skeletons of glyph outlines): no general algorithm gives a handwriting order.
- **Bundling Hershey data in the engine**: a data licence the engine does not need to carry, and no accented letters.
- **Text-layer presets that follow strokes**: they would need glyph strokes in the text pipeline, which has outlines only.
- **Layout by glyph number**: glyph numbers are not contiguous in a file; the file order is what font readers use.

## Backwards compatibility

Class: Added asset kind and shape kind, MINOR, gated by version 1.2 (V5). No existing document is affected.

## Open issues

- Characters outside U+0020 to the font's last glyph (accented letters): a font whose glyphs are in another order needs a map.
- Kerning, alignment (centre, right) and line width limits.
- Other single-line formats (SVG fonts, `.svg` glyph sets).
