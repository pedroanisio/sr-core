# SREP 18 — Add render reports and inert-attribute findings

## Abstract

Four engines render the same document, and none of them says what happened to the picture. This SREP
defines a **render report**: one JSON format, with a registry of finding codes, that every engine writes
for an output when the output asks for it with `output/@report`. It also defines **inert-attribute
findings**, a closed table of attributes that are valid but have no effect, which validators and engines
report at `info` severity. Other SREPs add their findings to the registry: legibility
([SREP 19](srep-0019.md)), text fit ([SREP 20](srep-0020.md)), fonts ([SREP 21](srep-0021.md)) and engine
support ([SREP 22](srep-0022.md)).

## Motivation

The evidence comes from the scenes on the maintainers' machines: 460 distinct scene documents, 65 of them
production scenes, and the engines' sources.

- **Nothing reports the outcome of a render.**
  - The reference implementation's diagnostics cover the document: XML, structure, the XSD and Schematron
    rules, and assets.
  - `accessibility` has `flashCheck` and `contrastCheck`, and `safeArea` has `enforce`, but the schema
    does not say where their verdicts go, and no two engines write the same thing.
  - A tool that wants to know whether a render is any good, such as a review sheet or CI, has nothing to
    read.
- **Attributes that validate and do nothing.**
  - 102 shapes set `strokeWidth` with no stroke paint, so no stroke is drawn.
  - 11 nodes start after the composition ends, so they are never drawn.
  - The FrameForge render engine found the same class of defect "in the wild" and reports it as
    `inert_style_key` and `inert-stroke-declaration`. Nothing in scene-render does.

## Specification

### Syntax

```xml
<!-- outputType gains -->
<xs:attribute name="report" type="xs:anyURI">
  <xs:annotation><xs:documentation>
    Where to write this output's render report (scene-render-report/1), relative to the document.
  </xs:documentation></xs:annotation>
</xs:attribute>
```

A new attribute with no default, accepted in every version (SREP 0, Versioning). No Schematron rules.

### Semantics

**1. When.**
1. An engine that renders an output with `report` MUST write the report file there, after rendering,
   whether or not the render succeeded.
2. It MAY also write reports when asked on its command line. How it is asked is not specified.
3. A render that stops on an error still writes the report, with the error among the findings.

**2. Form.** The report is one UTF-8 JSON object:

```json
{
  "format": "scene-render-report/1",
  "engine": {"name": "rs-scene-render", "version": "0.9.0"},
  "scene": {"sha256": "8e47…9b642", "version": "1.1"},
  "output": {"id": "out-master", "width": 1920, "height": 1080, "start": 0, "end": 292.167},
  "findings": [
    {"code": "INERT-I2", "severity": "info", "path": "/scene/composition/group[2]/shape[4]",
     "node": "gr0_chip", "message": "strokeWidth 2 with no stroke paint draws no stroke"}
  ]
}
```

| Field | Rule |
|---|---|
| `format` | exactly `scene-render-report/1`; MINOR additions add fields, never change them |
| `scene.sha256` | SHA-256 of the document's bytes as read |
| `output` | the output as rendered: its id, pixel size and time range |
| `code` | a code from the registry (4), or `X-<engine>-<code>` for an engine-specific finding |
| `severity` | `error`, `warning` or `info` |
| `path` | an XPath of the element concerned (`/scene/composition/layer[2]`), with 1-based positions among same-name siblings; `/scene` when nothing narrower applies |
| `node` | the element's `id`, when it has one |
| `time` | `[start, end]` in composition seconds of the output's timeline, when the finding concerns a time |
| `measured`, `limit`, `unit` | the quantity found, the threshold it was compared with, and its unit, when a check measured one |
| `message` | for people; its wording is not part of the contract |

**3. Determinism.** The report MUST NOT contain timestamps, host names or paths outside the document's
folder. Findings are sorted by `time[0]` (findings without a time first), then `code`, then `path`. The same
document, engine version and output produce the same bytes.

**4. Registry.** The codes this SREP defines:

| Code | Severity | Finding |
|---|---|---|
| `XSD` | error | the document fails the XSD |
| `SCH-<id>` | error | a Schematron assert fails, e.g. `SCH-C3` |
| `ASSET-MISSING` | error | an asset file is missing or fails its `sha256`/`cacheSha256` |
| `TXT-FIT` | warning | text does not fit its box at the size drawn (after `autoFit`); `measured` is the overflow in pixels |
| `TXT-CUT` | warning | characters were dropped by `maxLines` or `overflow="clip"`/`"ellipsis"`; `measured` is how many |
| `ACC-FLASH` | per `flashCheck` | the existing photosensitivity check |
| `ACC-CAPTIONS` | error | `requireCaptions="true"` and an output without captions |
| `LEG-CONTRAST` | per `contrastCheck` | the existing contrast check |
| `SAFE-AREA` | per `safeArea/@enforce` | the existing safe-area check |
| `INERT-I1` … `INERT-I8` | info | an inert attribute (5) |

Codes added by other SREPs: `LEG-SPEED`, `LEG-SHORT` and `LEG-SIZE` (SREP 19); `FONT-SUB` and `FONT-GLYPH`
(SREP 21); `SUP-APPROX` and `SUP-REPORTED` (SREP 22). A new code needs an SREP.

**5. Inert attributes.** An inert attribute is valid and has no effect on the picture. Validators and
engines report each as `INERT-<rule>` at `info` severity; never as errors, because the document means what
it says, only less than its author thought.

| Rule | Condition |
|---|---|
| I1 | `stroke` is not transparent and `strokeWidth` is 0 or absent |
| I2 | `strokeWidth` > 0 and `stroke` is transparent or absent |
| I3 | `dash`, `dashOffset`, `strokeCap`, `strokeJoin` or `miterLimit` on an element that draws no stroke (I1, I2) |
| I4 | `points`, `innerRadius`, `outerRadius`, `innerRoundness` or `outerRoundness` on a `shape` other than `polygon` or `star` |
| I5 | `path` on a `shape` other than `path` |
| I6 | `matteMode` or `matteVisible` without `matte` (not on `transition`) |
| I7 | `volume`, `mute` or `audioBus` on a layer whose asset has no sound (image, text, vector, code, formula, chart, generator, audiogram) |
| I8 | a node whose window lies wholly outside [0, project `duration`), so it is never drawn |

The set is closed. A later SREP adds a rule only with a condition that is inert under the conventions, the
definitions and every accepted SREP.

### Defaults and the neutral case

With `report` absent no file is written. Findings never change pixels. A document that does not use
`report` renders byte for byte as before.

## Rationale

- **One format for the outcome.** A review sheet, CI or a packaging tool should not parse four engines'
  logs. The codes are few and stable, and engine-specific findings have a namespace (`X-<engine>-`), so
  engines can report more without breaking readers.
- **The existing checks gain a place to report.** `flashCheck`, `contrastCheck` and `safeArea/@enforce`
  already decide verdicts; the registry names them.
- **Inert findings are information, never errors.** The XSD already rejects unknown attributes, so the
  remaining class is valid attributes without effect, whose value is in telling the author. The table lists
  only conditions that are inert by the definitions. `radius` on `rect` is not in it: [SREP 23](srep-0023.md)
  makes it draw.

## Rejected alternatives

- **Reports inside the video container** (metadata tracks, sidecar XML). JSON beside the output is read by
  every tool and needs no demuxer.
- **Inert findings as Schematron asserts.** Schematron can express most of them, but its asserts fail
  validation; an inert attribute is not an error.
- **An open list of codes.** Readers would have to guess what an unknown code means. Engine-specific codes
  have their own namespace instead.

## Backwards compatibility

- **Class: Added, MINOR (1.2).** One attribute with no default, accepted in every version.
- No valid document becomes invalid, and none renders differently.
- **Evidence.** The XSD change was applied to a copy of the canonical schema, and the 2,600 local scene
  documents that declare 1.0 or 1.1 were validated with both copies. No verdict changed.

sr-core carries the reference implementation of the format, as SREP 1 does for packages:
- the JSON Schema `report-1.schema.json`;
- `sr-lint`, which writes a report with the static findings (`XSD`, `SCH-*`, `INERT-*`);
- `sr-review`, which shows a report's findings on the section pages they fall in.

## Conformance

| Case | Checks | Expected |
|---|---|---|
| `srep-0018-report` | a scene with one I2 shape and one I8 node, and `output/@report` | the report validates against `report-1.schema.json` and lists exactly `INERT-I2` and `INERT-I8` |
| `srep-0018-failed` | as above with an image asset whose `sha256` is wrong | the render fails, and the report lists `ASSET-MISSING` |
| `srep-0018-deterministic` | the `report` case rendered twice | byte-identical reports |
