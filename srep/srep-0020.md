# SREP 20 — Define where lines of text sit in a text box

## Abstract

The definitions say how strokes, outlines, masks and cameras are drawn, but not where a line of text sits in
its box. This SREP makes normative what the Rust and Python engines already draw to the pixel: CSS 2.1
half-leading over the `hhea` ascender and descender of the face used, lines at a pitch of
`lineHeight` × `size`, the block placed by `verticalAlign` and each line by `align`. It adds text cases to
the compatibility kit, which has none. It changes no schema and no picture drawn by the reference
implementation.

## Motivation

- **The rule is unwritten.** D1–D27 do not cover text layout, and the kit has no case with text, so text,
  the thing explainer videos show most, is the one output no test compares across engines.
- **The engines agree, by accident.**
  - A text asset of 80 px `HHHH`, `lineHeight="1.2"` and `verticalAlign="middle"` in a 200 px box inks rows
    149–207 on both the Rust and the Python engine.
  - That is exactly the prediction of half-leading over the `hhea` metrics of the face used (DejaVu Sans:
    unitsPerEm 2048, ascender 1901, descender −483): baseline 207.70, cap top 149.38.
  - OS/2 typographic metrics (1556, −492) would put the same line 7 px higher. An engine that switched
    would move every line of text, and no test would fail.

## Specification

### Semantics

For a text asset of box w × h, `size` s and `lineHeight` k, drawn as n lines after wrapping:
- A = hhea.ascender / unitsPerEm and D = −hhea.descender / unitsPerEm of the primary face, the face the
  asset's own style selects;
- when `hhea` is absent, or its ascender and descender are both 0, OS/2 `usWinAscent` and `usWinDescent`
  are used instead.

1. **Line pitch** L = k · s. **Block height** B = n · L.
2. **Block top**, in the box (+y down):
   - `verticalAlign="top"`: t = 0;
   - `middle`: t = (h − B) / 2;
   - `bottom`: t = h − B.

   The block may extend outside the box.
3. **Baseline of line i**, counted from 0: yᵢ = t + i · L + (L − (A + D) · s) / 2 + A · s. This is CSS 2.1
   §10.8.1 half-leading, with the content area given by the font's ascent and descent.
4. **Horizontal placement.** Line i, of advance width aᵢ (shaped advances, with `letterSpacing` and
   `tracking`), starts at:
   - x = 0 for `start` and x = w − aᵢ for `end`, in the inline direction; with `direction="rtl"`, start
     and end swap;
   - x = (w − aᵢ) / 2 for `center`;
   - `justify` widens the word gaps of every line but the last until aᵢ = w, never the letter spacing.
5. **Order.** `autoFit` chooses s before steps 1–4. `maxLines` and `overflow` then drop lines.
6. With a render report ([SREP 18](srep-0018.md)), a block taller than its box is `TXT-FIT` and dropped
   characters are `TXT-CUT`.

### Defaults and the neutral case

No syntax changes. The rules state what the reference implementation draws today.

## Rationale

- **It is what the engines do,** measured above; codifying it moves no existing text.
- **It is CSS's model,** so text in a browser preview sits where the render puts it.
- **No special case for one line.** With half-leading, a single line centred by `verticalAlign="middle"`
  sits optically centred. The FrameForge engine needed a separate rule for single lines because its
  multi-line model top-anchors on a baseline grid.

## Rejected alternatives

- **OS/2 typographic metrics (`sTypoAscender`, `sTypoDescender`).** They are the better-designed metrics,
  but choosing them would move every line of existing text by several pixels.
- **Leaving text to each engine.** Text is where engines are most likely to drift, and the kit could not
  catch it.

## Backwards compatibility

A Semantics clarification of existing behaviour. No document changes validity. Documents render as before on
the Rust and Python engines; an engine that seats text differently changes to match.

## Conformance

`make_cases.py` generates a pinned test font: unitsPerEm 1000, hhea ascender 800 and descender −200, every
glyph a rectangle from x 50 to 550 and from the baseline up to 700 units, advance 600. Text `HH`, size
100 px, `lineHeight="1.5"`, in a box placed at (100, 30).

| Case | Checks | Expected |
|---|---|---|
| `srep-0020-text-top`, `-middle`, `-bottom` | one line in a 400 × 300 box (2, 3) | ink rows: `top` 65–135; `middle` 140–210; `bottom` 215–285 |
| `srep-0020-text-lines` | three lines, `verticalAlign="top"`, box 400 × 450 (1, 3) | baselines at y = 135, 285 and 435 |
| `srep-0020-text-align` | the one-line case with `align` `start`, `center`, `end` (4) | ink columns 105–215, 245–355, 385–495 |

The values follow from the rules with the test font:
- A = 0.8 and D = 0.2, so at s = 100 the content area is 100 px, the pitch L is 150 and the half-leading 25.
- With `top`, the baseline is at 30 + 0 + 25 + 80 = 135, and the ink rises 70 px above it.
- A line of two glyphs advances 120 px, and each glyph inks 5–55 px of its 60.

`make_cases.py` computes every expected value from the rules.

## Open issues

- **Mixed-size spans.** The pitch comes from the asset's `size`. Whether a larger span grows its line, as
  CSS does, is not yet measured on the engines.
