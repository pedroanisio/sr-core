# SREP 0 — Add reactive values

## Abstract

[SREP 12](srep-0012.md) names, as its MF4 building block, "attributes bound to value trackers and expressions,
evaluated per frame without replay", with the bar "any frame alone equals the played frame" (line 255). This
SREP is that block. A new asset, `value`, is a named number that draws nothing: it carries keys, an expression
or a link like any property, and every expression, link and chart in the document reads it through
`prop("id.value")`. With `step` and `update` it is a **time fold**: its state advances in fixed steps from its
start by an update expression that sees the previous state, the step index, the step's time and seeded draws,
and the value at any composition time is the state after the last step at or before that time, computed from
the step count alone. With `count` and `update` it is an **index fold**: at each frame the update runs a fixed
number of times, which gives sums and quadratures. Values that read each other advance together in gather form.
Steps and counts are bounded by the document. Everything a 1.7.1 document can say renders as before.

## Motivation

- **The plan depends on it.** SREP 12 counts shots 5 (an Einstein solid whose packets hop between atoms, with
  F1) and 9 (a signal wound around a circle, its centre of mass tracing the Fourier transform) under MF4, and
  CL3 "binds charts to live counts" through it (line 265). The SRC-17 measurement (2026-10-24) scored 5 as
  custom ("the hops are keyed by hand") and 9 as custom ("the centre of mass and the transform plot are
  hand-written expressions").
- **A named value without a node does not exist.** The document animates properties of nodes and assets.
  An author who wants one number that several things follow today animates a hidden group's opacity and reads
  `prop("g.opacity")`: it works, and it is a workaround that a reader must decode. `param` is static per
  render and `bind` copies it once; neither is a tracker.
- **Expressions cannot accumulate.** D25 excludes loops and assignment, and `prop` reads keys and links, never
  expressions, so no expression can depend on its own earlier value: an integral, a running count, a
  population and a random walk are not expressible. The reference's `link` with `follow` is the one stateful
  looking thing in the format, and it is computed each frame as a weighted sum of the source's history
  (`crates/sr-eval/src/eval.rs:522-580`), which is the right shape: a result fixed by time, never by the frames
  rendered before.
- **Manim's answer is the wrong one for a format.** Manim's `ValueTracker` and updaters mutate state as the
  animation plays; a frame is reachable only by replaying from the start (SREP 12 line 145, "updaters replay
  from the start"). SREP 14 rule 1 forbids that: state at t is the state after stepping from the start to the
  last step at or before t, whatever was rendered before. This SREP states the fold so that an engine may keep
  checkpoints and a reader may compute any frame alone, and both get the same number.
- **A sum needs a bound.** The transform of shot 9 is a mean over a few hundred samples at every frame; the
  language has no loop, and a loop driven by the document must terminate. An index fold with a document-stated
  `count` and a schema bound is a loop whose bound ordinary code owns (rule 5 of the LLM-output policy in
  `CLAUDE.md` applies to the same shape of risk).

## Specification

### Syntax

The diff is against `schema/scene-render.xsd` at 1.7.1 and `schema/scene-render.sch`. It is stated here for
the schema editor; the schema files are not changed by this draft.

**1. The `value` asset.** `assetsType` (xsd:2387) gains `<xs:element name="value" type="valueAssetType"/>`,
with:

```xml
<xs:complexType name="valueAssetType">
  <xs:annotation><xs:documentation>
    A named number that draws nothing, read by prop("id.value"), propAtTime and link source="id.value".
    With step and update it advances in fixed steps from start (a time fold); with count and update
    its update runs count times at every frame (an index fold); otherwise its keys, expression or link
    give it, as any property.
  </xs:documentation></xs:annotation>
  <xs:group ref="animationElements" minOccurs="0" maxOccurs="unbounded"/>
  <xs:attribute name="id" type="xs:ID" use="required"/>
  <xs:attribute name="value" type="numberListType" default="0"/>
  <xs:attribute name="start" type="nonNegativeDecimal" default="0"/>
  <xs:attribute name="step" type="positiveDecimal"/>
  <xs:attribute name="count">
    <xs:simpleType><xs:restriction base="xs:positiveInteger"><xs:maxInclusive value="1000000"/></xs:restriction></xs:simpleType>
  </xs:attribute>
  <xs:attribute name="update" type="expressionString"/>
  <xs:attribute name="between" default="hold">
    <xs:simpleType><xs:restriction base="xs:string">
      <xs:enumeration value="hold"/><xs:enumeration value="linear"/>
    </xs:restriction></xs:simpleType>
  </xs:attribute>
  <xs:attribute name="seed" type="xs:unsignedLong"/>
</xs:complexType>
```

`value` is the animatable property (its keys, expression and link are the children, as for any property;
xsd:634 `animationElements`). `start` and `step` are seconds of composition time. `seed` is the seed of the
draws of rule 6, the project's seed when absent (as xsd:542 for expressions).

**2. Built-ins of an update.** `expressionType`'s documentation (xsd:522-534) and D25 gain, for an `update`
expression only: `value` is the state before the step, `index` the step or iteration index from 0, `count`
the step number (index + 1) in a time fold and the `count` in an index fold, `time` the step's time (a time
fold) or the frame's time (an index fold), `dt` the `step` (0 in an index fold), `random()` the draw of rule
6, and `draw(channel, i)` (two integer arguments) the shared draw of rule 6. The grammar is unchanged.

**3. Chart series follow values.** `chartSeriesType` (xsd:1702) gains `<xs:group ref="animationElements"
minOccurs="0" maxOccurs="unbounded"/>`, so `values` may carry `<link property="values"
source="count.value"/>` and a counter or bar chart shows a live count (CL3).

**4. Schematron.** A pattern `p-srep-reactive` after `p-srep75` (sch:851):

- `RV1` on `assets/value`: `boolean(@update) = (boolean(@step) or boolean(@count))` and
  `not(@step and @count)`: "a value has update with exactly one of step and count".
- `RV2` on `assets/value`: `not(@between = 'linear') or boolean(@step)`: "between applies to a time fold".
- `V17` on `/scene[@version` 1.0 to 1.7`]`: `not(assets/value)`: "value assets need version 1.8".

Two further constraints need the expression's text and are build errors of the engine, not Schematron:
`E1`, values that read each other with `prop` share `step` and `start` (rule 5); `E2`, a time fold's step
count at the composition's end (`compositionType/@duration`, xsd:1199) is at most 1,000,000 (rule 8).

### Semantics

1. **A value is a property without a node.** `value` holds a number or a number list (`numberListType`, as
   `scale` holds two). Keys, an expression and a link on `value` give it at any time by D13 and D25, exactly
   as a node's property; `prop("id.value")`, `propAtTime("id.value", t)` and `link source="id.value"` read
   it, from anywhere in the document, and read the fold's state when the value is a fold. A value draws
   nothing and has no time of its own: `time` in its expressions is composition time, as for an asset.
2. **The step count.** For a time fold with `start` s and `step` h, the number of steps at or before
   composition time t is n(t) = 0 when t < s, else ⌊(t − s) / h + 10⁻⁹⌋, with the same tolerance D25 gives
   `frame`.
3. **A time fold.** Its initial state s₀ is its keyed `value` evaluated at `start` (keys, expression and link
   as rule 1; a plain attribute is one key). For k ≥ 1, s_k = update(value = s_{k−1}, index = k − 1,
   count = k, time = start + k·h, dt = h). The value at composition time t is s_{n(t)} when `between` is
   `hold`, and s_n + (s_{n+1} − s_n)·u with u = (t − s)/h − n when it is `linear` (u clamped to [0, 1];
   before the start the value is s₀). The state s_k is a function of k alone: an engine that keeps the last
   state and steps forward, one that keeps checkpoints and one that recomputes from s₀ at every frame MUST
   produce identical values (SREP 14 rule 1; the seek check of rule 5).
4. **An index fold.** At composition time t, its state before the first iteration is its keyed `value` at t;
   for k = 0 .. count − 1, v ← update(value = v, index = k, count = count, time = t, dt = 0), in increasing
   k (SREP 14 rule 3 states the order of summation); the value at t is the final v.
5. **Reads within a step: gather form.** `prop` and `propAtTime` inside an update read every other property
   at the update's `time`. When a time fold reads another time fold, it reads that fold's state *before* the
   step (s_{k−1}): all folds of one `step` and `start` advance together, every update of step k sees every
   state of step k − 1, and a cycle of reads among them is allowed. Two folds of different `step` or `start`
   MUST NOT read each other (build error `E1`). An index fold may read any value at t, and no value reads an
   index fold inside an update. An update that produces a non-finite number is a render error.
6. **Draws.** `random()` in an update is D25's draw with the fold index in place of the frame:
   U(seed, index, site + channel·2³²) with U the unit draw of D24 (`DEFINITIONS.md`, convention 5.19) and
   site and channel as D25 states. `draw(channel, i)` is U(seed, channel, pack(index, i, 0)) with `pack` the
   D24 lattice packing of the random-streams draft; it depends on the seed, the channel, the step and i only,
   so two values with the same `seed` (or none, when both use the project's) see the same number at the same
   step. Neither carries state (SREP 14 rule 2).
7. **Chart series.** A `series` whose `values` is linked or expressed reads a number list each frame; a
   counter chart shows its first value, and the formatting of `chart/@format` applies to it unchanged.
8. **Bounds.** `count` is at most 1,000,000 (xsd), and n(duration) of a time fold is at most 1,000,000 at the
   composition's end (build error `E2`). An engine MUST NOT run a fold beyond those counts, whatever the
   expressions ask.
9. **Precision.** States are binary64; the update's operations are those of D25 in the written order. Within
   one engine the seek check is exact (rule 3). Between engines, folds whose updates use only arithmetic
   compare exact, and folds that use transcendental built-ins compare within the tolerance each kit case
   states (SREP 14 rule 5).
10. **Determinism.** Rules 2 to 9 meet SREP 14 rules 1 (fixed steps from a declared start; hold or linear
    between), 2 (draws from the D24 hash and integer indices), 3 (gather form, increasing summation) and 5
    (the seek check); no external data and no library are involved (rules 7 and 8).

Two applications the catalogue needs, stated so the kit can measure them:

- **Shot 9, the Fourier centre of mass.** With a signal g written as an expression of a sample time τ, a
  winding frequency f (a tracker with keys), N samples over a duration T, two index folds of `count="N"` give
  x = (1/N) Σ_k g(τ_k) cos(2π f τ_k) and y = −(1/N) Σ_k g(τ_k) sin(2π f τ_k), τ_k = k·T/N, and a node's
  position links to them. For g = cos(2π·3τ), T = 4, N = 400, x is 1/2 at f = 3 and 0 at f = 2 (the table).
- **Shot 5, the Einstein solid.** N cells on a ring, one time fold per cell, one seed. At every step each
  cell's update computes the same hop from the shared draws: src = ⌊draw(0, 0)·N⌋, dst = src ± 1 by
  draw(1, 0) < ½, and the hop happens when `prop("e<src>.value") > 0` (the state before the step, rule 5);
  the cell loses one packet when it is src and gains one when it is dst. The total is conserved exactly at
  every step, the trajectory is a function of the seed and the step, and any frame alone equals the played
  frame (the table).

## Rationale

- **An asset, not a parameter.** Parameters are template inputs fixed per render; a value changes with time
  and is read like a property. Assets already own animatable properties that nodes and expressions read
  (`formula/@progress`, `chart/@progress`), and the reference resolves an asset's id as a `prop` owner
  (`crates/sr-eval/src/program.rs:3650-3660`); the value asset is that mechanism with nothing to draw.
- **A fold, not an updater.** An updater is a procedure run as the animation plays; a fold is a function of
  (initial state, update, k). Only the second can be seeked, compared between engines and tested by a table.
- **Gather form, with a shared step.** Simultaneous update is the only rule under which a cycle of reads has
  one meaning and the result does not depend on the order of the values in the document (SREP 14 rule 3).
  Requiring one step and start for values that read each other avoids defining what a fold of step 1/60
  sees of a fold of step 1/30 between its steps.
- **Two draws.** D25's `random()` is per call site and property, which is right for independent jitter and
  wrong for a hop that every cell must agree on; `draw(channel, i)` is the shared one. Both are the D24
  hash, as SREP 14 rule 2 requires.
- **Bounds in the schema and at build.** A document that asks for 10⁷ iterations per frame is refused before
  rendering, not rendered slowly; the limit is a count and the same on every engine.
- **Hold by default.** A simulation's frame between two steps shows the earlier step (SREP 14 rule 1 asks
  the SREP to say which); `linear` is for integrators drawn as smooth curves.

## Rejected alternatives

- **A stateful `random` sequence in expressions.** It makes the value depend on the calls before it, the
  replay that SREP 14 forbids.
- **Lambdas or loops in the expression language.** A loop whose bound is an expression is a loop the model
  or the author controls; the fold's bound is an attribute the schema checks.
- **A list-valued state with an `at(i)` built-in.** It would let one value hold a whole lattice and spare
  the per-cell values of shot 5. The language has no arrays (D25); adding them touches every built-in. Left
  as an open issue.
- **Reading a fold's state after the step (sequential update).** The result would depend on document order
  and forbid cycles; rejected for SREP 14 rule 3.
- **A `tracker` node in the composition.** A node has a transform, a time and a place in the draw order
  that a number does not need, and nodes are not readable from assets.

## Backwards compatibility

- Every 1.7.1 document validates and renders unchanged: `value` is a new asset, the built-ins are new names
  meaningful in `update` only, and `series` gains optional children.
- A 1.8 document that uses them is refused by a 1.7 validator (unknown element or attribute), as V17 states.
- D25's `random()` keeps its meaning in every expression that is not an update.

## Open issues

- **List-valued folds.** A lattice of a hundred cells needs a hundred values and an N-way `prop` lookup in
  each update; a list-valued state with an `at(i)` read and a `count`-sized output would make shot 5 ten
  lines. It needs arrays in the language or a dedicated element; left to the editor.
- **The cost of a fold per frame.** Rule 3 allows checkpoints and rule 8 bounds the steps; an engine that
  renders frames in parallel recomputes or shares checkpoints. SREP 14's open issue on the seek check's cost
  applies.
- **D13 curves of the initial keys.** Rule 3 takes s₀ from the keyed value at the start; the reference module
  interpolates keys linearly because the curves are not its subject. The kit case states a plain attribute.
- **Index folds reading time folds at `time`.** Rule 5 reads the time fold's value at t (rule 3's hold or
  linear value), not a step state; whether a fold should see the step boundary is open.
