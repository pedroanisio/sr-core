# SREP 89 — Amend SREP 72: the supersample clamp keeps values above 1

## Abstract

SREP 72 §4 clamps the supersampled result to [0, 1] per channel, to remove Lanczos overshoot. The working space is
linear and may hold values above 1, so the clamp also cuts every highlight above 1 before the frame reaches colour
finishing (tone mapping) and output. As a result, a frame at `supersample="2"` differs from the same frame at
`supersample="1"` by more than antialiasing. This SREP replaces the fixed upper bound 1 with the larger of 1 and the
largest sample the filter reads. A document whose samples all lie in [0, 1] renders the same bytes as under SREP 72.

## Motivation

- **SREP 72 §4, "Edges and range":** "The mean is taken in the working space before output encoding. The result is
  clamped to [0, 1] per channel, removing Lanczos overshoot."
- **The clamp exceeds its stated purpose.** Overshoot is a value beyond the range of the samples the kernel reads.
  A flat region of value 4.0 has no overshoot; its weighted mean is 4.0, but the clamp makes it 1.0.
- **Measured on the reference** (rs-scene-render `fix/atlas-findings` 73ad8e47, lavapipe, `crates/sr-gpu/tests/bloom_hdr.rs`):
  - `supersampled_hdr_reaches_the_tone_mapper`: an emissive region of 4.0 with `toneMap="reinhard"` or `"aces"`. At
    n = 1 the tone mapper receives 4.0. At n = 2 and 3 (box and lanczos3) it receives 1.0, so the frame is darker.
  - `supersampled_hdr_survives_without_tone_mapping`: with no tone mapper, n = 1 keeps 4.0 in the frame and n = 2 gives 1.0.
  - Both tests are `#[ignore]`d with the reason "needs an SREP 72 amendment". The reference implements SREP 72 as written.
- **Where it was found:** while fixing the bloom item of the atlas v2 ENGINE_FINDINGS (internal). The reference now runs
  colour finishing on the filtered frame (an order fix that SREP 72 allows); the range is the part that needs this SREP.

## Specification

Replaces the second and third sentences of SREP 72 §4 "Edges and range":

> The mean is taken in the working space before output encoding. For each channel, the result is clamped to
> [0, max(1, M)], where M is the largest value of that channel among the samples with a non-zero weight in the sum.
> This removes Lanczos overshoot above the samples and below 0, and keeps values above 1 that the samples hold.

Nothing else in SREP 72 changes. The Schematron does not change. The XSD changes in documentation only: the
`supersample` attribute's text "clamped to [0, 1]" becomes "clamped to [0, max(1, M)], M the largest sample of
non-zero weight. SREPs 72 and 89."

### Neutral case

- If every sample of a channel within the support lies in [0, 1], then M ≤ 1, the bound is [0, 1], and the result is
  bit-identical to SREP 72. This covers every document with no working value above 1.
- `box` never overshoots: its result lies between the smallest and largest sample, so for `box` the clamp only
  removes negative values (none arise from non-negative samples). For non-negative samples, `box` returns the plain mean.
- `supersample="1"` is unchanged (no filter runs).

### Reference implementation

rs-scene-render d7f12a2f (`fix/atlas-findings`): the `SUPERSAMPLE` fragment shader of `crates/sr-gpu/src/shader.rs`,
which filters one axis per pass, keeps the per-channel maximum of the samples with `wts[t] != 0` (starting from 1) and
writes `clamp(sum / ws, vec4(0.0), hi)`. The two tests above run again and pass on lavapipe (`bloom_hdr`: 5 passed,
0 ignored, sr-llvm container, 2026-10-10).

## Backwards compatibility

Documents whose working values never exceed 1 render the same bytes. Documents with values above 1 that use
`supersample > 1` change: their highlights now reach colour finishing and output as they do at n = 1. SREP 72 goes into
schema 1.6.0, which was being released on 2026-10-10; the fewer documents that rely on the clamp, the cheaper the change.

## Conformance

The cases are in `conformance/srep_cases/srep-0089.json`, written by `conformance/tools/srep89_cases.py`. None is
pending: on 2026-10-11 all three pass on the reference, rs-scene-render main 1c989c9f (release build, llvmpipe), with
`conformance/run.py --cases srep-0089-supersample-hdr`. Each of the three regions of each case measures 188.0 against
the expected 187.5, within the tolerance, at n = 1, at n = 2 with `box` and at n = 3 with `lanczos3`; SREP 72 as
written would give 99.1 at n = 2 and 3. The n = 1 control, which no filter touches, measures the same 188.0.

The case `srep-0089-supersample-hdr` is three documents, one per row: the kit renders one document per case, and
`supersample` belongs to `project`. Each fills the 640 × 360 frame with a white rectangle under an `exposure` effect of
2 stops, a flat working value of 4.0 (DEFINITIONS, Colour grade: `exposure` scales by 2^exposure), and has
`colorManagement` with `toneMapping="none"` and `exposure="-3"`. The kit reads 8-bit PNG, where 4.0 and 1.0 both
encode to 255; the finishing exposure of -3 stops brings the region into the PNG's range. It is colour finishing,
after the filter (SREP 72 §4: the mean is taken in the working space before output encoding). The expected value is
4.0 × 2^-3 = 0.5, 187.5 in sRGB code values, at the centre of the frame and at two corners (the corners check the
weights renormalised at the frame's edges). Under SREP 72 as written the filter gives 1.0, and the region is
1.0 × 2^-3 = 0.125, 99.1.

| Case | Checks | Tolerance |
|---|---|---|
| `srep-0089-supersample-hdr-n1` | no filter (`supersample="1"`): the value the other two must equal | 3 code values |
| `srep-0089-supersample-hdr-box-n2` | `supersample="2"`, `box` | 3 code values |
| `srep-0089-supersample-hdr-lanczos3-n3` | `supersample="3"`, `lanczos3` | 3 code values |

**Assumption:** `colorManagement/@exposure` scales by 2^exposure, as the `exposure` effect does; the schema does not
define its unit. The reference agrees with it (the n = 1 control measures 4.0 × 2^-3 = 0.5), but the schema still does
not state it. An engine that applied it before the filter would give the same values (the region is
flat), so the cases do not depend on that order.

The existing `srep-0072-supersample-box` and `-lanczos3` cases (values in [0, 1]) are unchanged.

## Open issues

- **Per-axis vs final clamp.** SREP 72 states one clamp on the separable 2D result. The reference clamps after each
  axis pass. For values in [0, 1] with `lanczos3`, the two can differ where the first pass overshoots. The existing kit
  cases pass at 3 code values either way. This SREP does not settle it; the schema editor may want one form stated.
- **Highlights next to edges.** With `lanczos3`, a pixel next to a bright edge may still undershoot towards 0 (clamped)
  or ring up to M (kept). Whether a tighter de-ringing bound (the local minimum and maximum) is wanted is left open,
  because it would change bytes for documents within [0, 1].
