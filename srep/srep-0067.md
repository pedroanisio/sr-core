# SREP 67 — Add compute accumulation, a density tonemap, `iterate`, and serial image operations

## Abstract

This SREP adds four related pieces, for phase 3 of the engine plan.

1. **`<compute>`**: a node that runs a WGSL compute shader over a count of invocations. The shader adds
   integer amounts into a per-pixel histogram, using atomic fixed-point accumulation.
2. **A density tonemap stage, `<tonemap>`**: turns that histogram into a picture with a log-density curve,
   gain and gamma.
3. **`<iterate steps="N">`**: advances the stateful nodes inside it N steps within one frame, with a mandatory
   step ceiling and an optional convergence stop.
4. **Two serial image operations**, as effect types: `error-diffusion` (Floyd–Steinberg, Atkinson and others) and
   `segmented-sort` (pixel sorting). Both are specified in integer arithmetic.

The determinism claim of `<compute>` covers the accumulation only. Given the same set of contributions,
the histogram is identical in any order. The float computation of the points is not covered.

## Motivation

**The owner's 72-cell atlas test (2026-10-09, not published).**

- **11 cells** need scatter accumulation followed by a density tonemap. They are the Clifford, De Jong, Lorenz,
  Aizawa and Ikeda attractors, the Nebulabrot, the fractal flame, the Barnsley fern, the chaos game, the
  Chirikov standard map, and random walks. Each iterates millions of points and counts them into a histogram;
  the owner's note gives 60 million points for the Clifford attractor. A pixel shader cannot write to arbitrary
  pixels, and a raw histogram is unreadable without a log-density tonemap. This is the second-largest gap
  after generated geometry (SREP 66, 18 cells).
- **2 cells** need serial image operations: error-diffusion dithering (Atkinson, Floyd–Steinberg) and pixel
  sorting. Each output pixel depends on pixels processed before it, which a pixel shader cannot express.
- Reaction–diffusion in a still needs about 9,000 steps (the owner's figure). Today a persistent shader
  advances one step per frame (SREP 68).

**What exists today**, checked at `rs-scene-render` commit `c09b58a`:

- **Effects.** The only programmable effect is `effect type="shader"`: a GLSL fragment shader with ISF
  multi-pass and `PERSISTENT` buffers (`crates/sr-gpu/src/shader.rs`). There is no compute stage in the
  format.
- **Persistent buffers.** Persistent ISF buffers advance once per rendered frame. A seek replays the
  earlier frames of the whole scene (`crates/sr-gpu/src/render.rs`, `render_with`).
- **Working textures.** These are `Rgba16Float` (`crates/sr-gpu/src/resources.rs:13`). Float accumulation by
  blending in such a texture loses counts above 2048, the largest float16 range where integers are exact.
  Its result also depends on the order of blending.

### Semantics

**1. The compute stage.** `src` is a WGSL source file. If `sha256` is present, the engine checks it; a mismatch is
error **CMP10**. The engine prepends a prelude that declares the following, exactly:

```wgsl
struct SrCompute { size: vec2<u32>, invocations: u32, frame: i32, time: f32, seed_lo: u32, seed_hi: u32, nparams: u32 }
// bound by the engine; the author does not declare bindings
fn sr_accumulate(x: i32, y: i32, channel: u32, amount: u32)     // integer amount
fn sr_accumulate_f(x: i32, y: i32, channel: u32, amount: f32)   // amount quantised by fractionBits (below)
fn sr_param(index: u32) -> f32                                  // the index-th param child, in document order, as f32; 0 when absent
fn sr_hash(v: u32) -> u32                                       // the PCG hash of SREP 39, item 1
var<uniform> sr: SrCompute;
```

The author MUST define `fn sr_point(i: u32)`. The engine calls it exactly once for each `i` in
0 … `invocations` − 1, in an unspecified order and with unspecified concurrency.

- `sr.seed_lo` and `sr.seed_hi` are the low and high 32 bits of `mix64(project/@seed ⊕ mix64(compute/@seed))`,
  with `mix64` as in SREP 66, Semantics 4.
- `sr.frame` is the frame index and `sr.time` the composition time, in seconds.
- `sr.size` is (`width`, `height`).

A shader that fails to compile is error **CMP11**. A shader that declares its own bindings in group 0 is error
**CMP11**.

**2. The histogram.** The histogram H has `channels` planes of `width` × `height` cells. Each cell is an unsigned
integer of at least 64 bits, and every cell is zero at the start of each frame.

- `sr_accumulate(x, y, c, a)` adds `a` to H[c][y][x] when 0 ≤ x < width, 0 ≤ y < height and c < channels.
  Otherwise it does nothing.
- `sr_accumulate_f(x, y, c, a)` first quantises `a` to `q = min(floor(max(a, 0) · 2^fractionBits + 0.5), 4294967040)`,
  then adds `q` as above. The bound 4294967040 = 2³² − 256 is the largest f32 below 2³². f32 cannot represent
  2³² − 1, so the quantised amount is kept below 2³², as the carry of Engine impact requires.
- Plane 0 is the density. With `channels="4"`, planes 1 to 3 are colour sums for red, green and blue. They are in
  the same fixed-point units, as display-encoded values in [0, 1].

**Determinism (normative).** After the frame's invocations, H MUST equal the exact integer sum of the amounts of
all `sr_accumulate` calls made, and this MUST NOT depend on the order or concurrency of the invocations. This is the
whole of the claim. This SREP does **not** claim that the calls made, or the float arguments passed to them, are the
same on different GPUs, drivers or engines. WGSL float arithmetic may differ between implementations, and a chaotic
map such as the Clifford attractor (xₙ₊₁ = sin(a·yₙ) + c·cos(a·xₙ), yₙ₊₁ = sin(b·xₙ) + d·cos(b·yₙ)) separates two
orbits that start 1 ULP apart within a few dozen iterations. Two hosts can therefore produce different histograms
from the same document. Each one is still exactly the sum of its own contributions.

**3. The density tonemap.** Let `n = H₀[y][x] / 2^fractionBits` for each pixel, and let `N` be the `reference`
attribute. With `reference="max"`, N is the largest `n` in the frame (exact, from H).

    v = 0                                         if N = 0
    v = clamp(ln(1 + gain·n) / ln(1 + gain·N), 0, 1)    if scale = "log"
    v = clamp(n / N, 0, 1)                         if scale = "linear"
    v' = v^(1/gamma)

- With `channels="1"`, the pixel's colour is `ramp(v')`. `ramp` is the list of colours in the `ramp` attribute,
  placed at equal intervals on [0, 1] and interpolated linearly per channel in **display-encoded** values. These
  are the code values of CONVENTIONS 1.4, so `#808080` at v' = 1 displays as 128.
- With `channels="4"`, let the mean colour be `m_c = H_c / H₀` for c = 1, 2, 3 (0 where H₀ = 0). The pixel is
  `(m₁·v', m₂·v', m₃·v')`, in display-encoded values.
- The alpha is 1 when `alpha="opaque"`, and `v'` when `alpha="density"`.

The node draws this width × height picture with its top-left corner at its local origin, one histogram cell per
pixel, under the node's transform, timing, opacity and blend. Without a `tonemap` child, the defaults apply.

The tonemap evaluates a logarithm in floating point. A conforming result is within **1 code value** (8-bit) of the
formula. This tolerance applies to the tonemap only, not to H.

**4. `iterate`.** A *stateful node* is one whose picture depends on its own earlier steps:

- a `shader` effect with `PERSISTENT` ISF passes (the effect is stateful on each node it is applied to);
- a stepping program (SREP 69).

Inside an `iterate`, at each frame f with time t, every stateful descendant restarts from its zero state and
advances `steps` steps with its inputs at time t. The frame is then drawn from that state. One step of a
persistent shader is one evaluation of all its passes. The node's state does not carry over from frame f − 1, so
an `iterate` frame does not depend on which frames were rendered before it.

- With `until="converged"`, after every `checkEvery` steps the engine compares each persistent buffer with its
  value `checkEvery` steps earlier. It stops early when the largest absolute difference in any texel and channel is
  at most `tolerance`. `steps` remains the ceiling, and iteration never exceeds it.
- The number of steps taken SHOULD appear in the render report (SREP 18).
- The convergence test compares float values, so the step at which iteration stops may differ between hosts.
  With `until="steps"` the step count is exact.

- **Uniforms of the steps.** For every step of frame f, `TIME` is t(f) and `TIMEDELTA` is the frame's own value:
  1/fps, and 0 at time 0, as without `iterate`. `FRAMEINDEX` counts the steps of that frame from 0.

Nesting `iterate` is not allowed (ITR2). A stateful node inside an `iterate` ignores its own `stepsPerFrame` and
`prewarm` (SREP 68).

**5. Serial operations: the domain.** `error-diffusion` and `segmented-sort` operate on the node's content
rectangle: its bounds in target pixels, rounded out to whole pixels. They do not operate on any margin. Each pixel's
colour is first converted to 16-bit integers: `I_c = round(clamp(e_c, 0, 1) · 65535)`, where `e_c` is the
display-encoded (sRGB transfer) value of the unpremultiplied colour, c ∈ {R, G, B}. The operations then run in
integer arithmetic. The result is converted back with `e_c = I_c / 65535`, and alpha passes through unchanged.

**Determinism (normative).** Given the integer input I, the output is exact. The conversion from the working
space to I involves floats and is not covered by this claim.

**6. `error-diffusion`.**

- **Palette.** `palette` is a list of colours, default `#000000FF #FFFFFFFF`, as 16-bit values `P_k = 257 · code8`.
- **Scan order.** Pixels are visited row by row from the top. Within a row they go from left to right; with
  `serpentine="true"`, odd rows (counting the first row as 0) go from right to left and the kernel is mirrored
  in x.
- **Working value.** W starts as I.
- **At each pixel.** The chosen colour Q is the palette entry that minimises Σ_c (W_c − P_k,c)². A tie goes to
  the lowest k. The output is Q. The error `E_c = W_c − Q_c` is an unclamped integer.
- **Diffusion.** For each kernel entry (dx, dy, w) with denominator D, W at (x + dx, y + dy) gains
  `floor(E_c · w / D)`, a floor toward −∞. Entries outside the rectangle are dropped. The kernels are:

| Kernel | D | Row y: (dx, w) | Row y+1: (dx, w) | Row y+2: (dx, w) |
|---|---|---|---|---|
| floyd-steinberg | 16 | (1,7) | (−1,3) (0,5) (1,1) | |
| atkinson | 8 | (1,1) (2,1) | (−1,1) (0,1) (1,1) | (0,1) |
| jarvis-judice-ninke | 48 | (1,7) (2,5) | (−2,3) (−1,5) (0,7) (1,5) (2,3) | (−2,1) (−1,3) (0,5) (1,3) (2,1) |
| stucki | 42 | (1,8) (2,4) | (−2,2) (−1,4) (0,8) (1,4) (2,2) | (−2,1) (−1,2) (0,4) (1,2) (2,1) |
| burkes | 32 | (1,8) (2,4) | (−2,2) (−1,4) (0,8) (1,4) (2,2) | |
| sierra | 32 | (1,5) (2,3) | (−2,2) (−1,4) (0,5) (1,4) (2,2) | (−1,2) (0,3) (1,2) |

**7. `segmented-sort`.**

- **Lines.** With `direction="horizontal"`, each row is a line, read left to right. With `"vertical"`, each column
  is a line, read top to bottom.
- **Key.** The key of a pixel is `luma = (13933·R + 46871·G + 4732·B) >> 16`, where the weights are the Rec. 709
  coefficients times 65536, rounded, and they sum to 65536. The keys `red`, `green` and `blue` take that channel.
- **Segments.** A segment is a maximal run of consecutive pixels on a line whose key k satisfies
  `round(low·65535) ≤ k ≤ round(high·65535)`. Pixels outside every segment stay where they are.
- **Sort.** Within each segment, the pixels (RGBA together) are reordered by key, ascending or descending by
  `order`. The sort is stable: equal keys keep their original order.

### Defaults and the neutral case

A document without these elements and effect types is unaffected. A `compute` node without a `tonemap` child uses
a log scale, gain 1, gamma 1, `reference="max"`, a black-to-white ramp and opaque alpha.

## Rationale

- **Integer accumulation.** Integer addition is associative, so the sum does not depend on the order of the
  threads. A float sum does, and a float16 texture also saturates. This is the only part that can be made
  bit-exact across GPUs, so it is the only part claimed.
- **A log-density tonemap.** This is the standard rendering for fractal flames and strange attractors. Without
  it, a few cells with very high counts take the whole range and the rest is black. Gain and a fixed `reference`
  keep animated renders from flickering as the maximum changes.
- **Iterate for stills only.** Restarting from the zero state each frame makes every `iterate` frame independent of
  render order. The animated case, with state carried between frames, is SREP 68.
- **Integer serial operations.** Error diffusion propagates rounding errors through the whole image, so float
  differences of 1 ULP change the pattern. Integer arithmetic with floor division makes the pattern a function of
  the input alone.
- **Effect types for the serial operations.** These are image-to-image operations on a node, like the existing
  `halftone` and `posterize`. The plan calls them the primitives `wavefront` and `segmented-sort`. `wavefront`
  describes how an engine can run error diffusion on a GPU: anti-diagonal fronts, where pixel (x, y) runs at step
  x + 2y for Floyd–Steinberg. That is an execution scheme, so it belongs under Engine impact, not in the format.

## Rejected alternatives

- **Float atomics** (`atomicAdd` on f32): WGSL has no float atomics. Even where an API provides them, the sum would
  depend on order.
- **Claiming determinism of the points.** The plan forbids this. Chaotic systems make it false.
- **A scene-wide `<iterate>` for animation.** Every step would pay for the whole scene. SREP 68 iterates per node
  instead.
- **GLSL compute.** The engine is WGSL-native (wgpu). One shading language for compute keeps the prelude to one
  definition.

## Backwards compatibility

The change is MINOR: new elements and effect types under the version gate V13. Existing documents are unchanged.

**64-bit cells from 32-bit atomics.** WGSL atomics are 32-bit. If each amount added is below 2³², an engine can keep
a low word and a high word:

- `old = atomicAdd(&lo, a)`;
- if `old + a` overflows 2³² (that is, `old > 0xFFFFFFFF − a`), then `atomicAdd(&hi, 1)`.

The final pair is exact whatever the order, because the number of overflows equals ⌊Σa / 2³²⌋.

**Not verified:**

- Real-GPU carry: unverified (no discrete GPU we may use). The rs-scene-render reference tests the two-u32 cells
  with per-cell sums near 2³² on llvmpipe only (`raster_effects::srep67_compute`).
- The error-diffusion kernel weights were checked against this table and the commonly republished values, not
  against the original publications (Floyd–Steinberg 1976, Jarvis–Judice–Ninke 1976, Stucki 1981, Burkes 1988,
  Sierra 1989), which could not be read.

## Open issues

- GPU watchdogs: a compute shader that runs too long is killed by the driver. This SREP sets no instruction limit
  on shaders. CMP12 covers memory but not time.
- Should H persist across frames (temporal accumulation) as an option? Today it is cleared every frame, which keeps
  frames independent.
- Hue and saturation sort keys need float conversion. They were left out to keep the sort exact.
