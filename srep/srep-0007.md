# SREP 7 — Adopt the conventions and definitions as normative semantics

## Abstract

`conformance/CONVENTIONS.md` (the spatial conventions and 24 rulings) and `conformance/DEFINITIONS.md` (the
numbered definitions D1–D27 and the preset tables P1–P2) become normative for the scene format. They take
precedence over the reference implementation's behaviour wherever they speak. Before this SREP, the conventions
were applied by every engine but had never been adopted through the process, and they named an outside
document as their first authority.

## Motivation

- **They already govern rendering.** The conventions change what scenes render, and both engines checked by the
  compatibility kit already follow them: all 17 cases pass on Rust and Python.
- **They never went through the process.** SREP 0 requires a Semantics SREP for anything the schema leaves
  unstated.
- **The authority order contradicted SREP 0.** The conventions made the C renderer's definitions the first
  authority, while SREP 0 makes the reference implementation's behaviour the baseline.
- **Their references couldn't be read.** They cited definitions D1–D27 and engine source files that are not
  published, so a reader could not check them.

## Specification

1. `conformance/CONVENTIONS.md` and `conformance/DEFINITIONS.md` are normative for scene format 1.1.
2. **Precedence**, in order:
   1. the XSD and its Schematron rules;
   2. `CONVENTIONS.md` (a §5 ruling applies where it differs from a definition);
   3. `DEFINITIONS.md`;
   4. for anything still unstated, the reference implementation's behaviour (SREP 0, Baseline).
3. **Stated explicitly** (no change to what engines render):
   - object3D rotations are right-handed about the scene axes (CONVENTIONS 2.5), while 2.5D layer rotations
     turn the other way (5.14);
   - an explicit camera with no `z` sits on the plane z = 0 (2.3).
4. Changes to either document are made through SREPs.
5. `CONVENTIONS.md` §4 lists the rules that have compatibility-kit cases. The rest are open for cases.

## Rationale

The definitions are copied in, not linked, so the specification is complete in one published place. Engine
impact notes, translator status and planning tables were left out; they describe one engine's work, not the
format.

The handedness difference between layers and 3D objects is kept, not unified:
- Each side follows its own precedent: compositing layers follow After Effects, and meshes follow the
  right-handed axes that glTF uses.
- Changing either would change existing renders.

Cases d2 and d3 fix both behaviours.

## Rejected alternatives

- **Unifying the rotation sense.** It would break every 2.5D layer animation or every object3D rotation in
  existing scenes.
- **Changing the default camera position now.** A camera that defaults to the implicit camera's distance
  would be more useful, but documents that rely on z = 0 would render differently. It is listed as an open
  question in `CONVENTIONS.md` §3, for its own SREP.

## Backwards compatibility

No rendering changes. The conventions were already in force in the engines, and the new cases pass on the
reference implementation and on Python.
